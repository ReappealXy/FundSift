# 真实样本与首个可用导入实施方案：待用户与 DeepSeek 审核

日期：2026-11-18。状态：**已获用户授权分阶段实施**。最初版本为只读调研与方案草案；用户后续明确授权实现，并在待核操作选择中确认“只读查看原文、标准值和待核原因，先交付真实导入”。以下保留原方案来源，并以本节和新增实施记录说明最新范围，不能把设计验收要求当成全部已完成。

当前确认：接受单格式技术预览；支付宝账户 CSV 优先盘点但不提前定死；取消币种默认值且不盲改旧值；P1 先行、通用底座并行、选定格式子集基准后再接解析器与 EXE。分页以案件持久 `data_version` 检查，同页版本与数据在同一读事务读取，版本变化明确提示刷新，不实现旧快照。首版待核只读，不提供假保存按钮、不加入人工改值及其审计功能。

## 1. 这一步究竟做什么

目标是交付一条真正可用的路径：**在 EXE 中选择一份已核实格式的真实账单，归档副本，解析记录，按已批准规则处理金额，保存到案件，查看真实流水、待核原因和原始出处，关闭重开后仍可查询。**

其中，样本清单、规则卡和 G0 是开发的验收依据；金额引擎、格式解析器、导入任务和真实列表才是用户在软件里使用的功能。这些要接起来交付，不能继续只增加核对工具而没有可用业务路径。

| 层次 | 解决的问题 | 完成后用户能看到什么 |
|---|---|---|
| 样本盘点、规则卡、G0 | 哪些文件是真的原件、怎样处理才算对 | 一份可审核的样本与判定依据，不会单独新增 EXE 功能 |
| 金额引擎与一个具体格式解析器 | 原始字段如何变成可信的标准记录 | 解析器通过逐行对答案，但仍需接入桌面流程 |
| 桌面真实导入交付 | 文件如何进入案件、失败怎么办、结果怎么看 | EXE 中完整导入一次，并能重启保存、查看待核和来源 |

按“真实清单 → 通用底座并行 → 选定格式子集基准 → 单格式技术预览 → 完整 G0 与其余格式”推进。首个格式由真实结构盘点后选择，不先假定微信、支付宝或建行一定最简单；支付宝账户 CSV 是优先候选。

## 3. WorkBuddy 参考了什么，怎样使用

本轮参考多个资金分析工作区中的记忆、处理说明、符号核验、余额纠错与少量相关历史会话。主要关注原始材料、解析中间件、并表结果、分析交付之间的分层，以及实际处理中发生过的错误。

资料中有过时基线、助手判断和后续纠错。**这些是设计线索，不是本轮重新验证的交易结论，更不是可直接导入产品的规则。** 尤其“余额异常等于缺行”“同秒抵消即可证明正确”等早期说法存在后续修正，不能照搬。没有执行旧案件脚本，也没有重新计算旧报告中的金额、行数或账户数。

以下 W01～W16 对应本地私有出处索引 `golden-samples/planning-2026-11-18/workbuddy-evidence.md`。索引记录实际文件路径与行号，已处于 Git 忽略目录；本方案只使用案例代号和通用经验，不带实名路径、账户和交易明细。案例代号是调研标记，不自动等同于 G0 的 `case_ref` 或样本角色。

| 编号 | 实践经验 | 建议融入设计 | 如何验收 |
|---|---|---|---|
| W01 | 历史摘要会错，补充材料还会使旧基线失效 | 每轮清单重新核对文件身份、版本和计数；加工件与原件分开 | 当前哈希与独立索引匹配，变更基线可追查，不能抄历史笔数 |
| W02 | 被“清洗”的原文失去证据价值 | 原始值与标准值分开，保留完整原始记录及来源；标记异常，不静默删交易行 | 原文逐字段与归档副本相符，修改标准值不覆盖原文 |
| W03 | 负号、方向标志、元/分含义因具体格式不同 | 每个结构版本独立确认 A～F、单位、方向词表、负号及零值政策 | 原文抽取正确、金额业务判定正确分别验收；不靠全取绝对值通过 |
| W04 | 方向缺失、“其它”、文字 null 等不能猜 | 真实空值、原文字面值与标准未知分开；原因独立保存 | 未知不变零、不默认支出；多原因不会因只解决金额而全清 |
| W05 | “可以退款”不等于“已退款”，空白状态不等于成功 | 保留平台原始交易状态；精确词表另行确认，避免与记录确认状态混淆 | `confirmed` 只表示字段与判定已确认；界面不把它翻译成“交易成功” |
| W06 | 某些支付路径的余额 0 是占位；一个文件内也可能混有不同余额口径 | 规则卡按业务类型说明余额适用范围，缺少可比前提就显示原因 | 不把占位零当真实资产余额，不用余额差自动改方向或制造交易 |
| W07 | 同一交易号可能多行；相同时间金额也可能是真实不同交易 | 首导只做同案文件哈希与批内来源坐标的身份控制 | 保留多重记录，不按交易号或时间金额指纹自动删行 |
| W08 | 长账号易失真，账号与卡号不同；原件自身也可能拼接异常 | 账号、卡号、交易号按文本保存，类型与来源保留；异常原文不擅改 | 前导零、长号和特殊字符保真；原件已失真时提示，不能声称恢复了未知数字 |
| W09 | 姓名、平台用户 ID、登录号、账号、绑定卡号不是同一身份 | 首导保留原字段，不按同名自动合并账户，不拿另一标识无痕补号 | 缺账户有原因；本方/对手、标识类型与来源不串位 |
| W10 | 支付宝账户明细与余额明细视角不同且可能重叠；镜像两侧也不能直接累加 | 清单与规则卡标明材料视角；将来跨文件汇总先定义可加范围 | 两类 CSV 不按同一表头处理；混合视角不能展示成一个未经解释的总收入 |
| W11 | 冲正、退款原笔与回转应保留；关联不明不一定等于金额不明 | 标记冲回依据，关联另行处理；首导不自动抵消或补造配对 | 两行均可回源；跨期只剩一边时不强行归零 |
| W12 | 扫描、OCR、转换件与电子原件的可靠性不同 | 清单区分原件、副本、转换件、加工件；第一轮选择已核实电子格式 | 转换件有上游出处；PDF/OCR 不因后缀或有文字层而被当成已支持格式 |
| W13 | 合同、口供、回单与流水可能口径不同 | 材料陈述和交易记录分别登记，差异进入问题表 | 不用预期损失或口头陈述补金额、补流水、改方向 |
| W14 | 同秒交易不保证有真实先后，余额自洽也不证明逐笔正确 | 显示用稳定排序，余额比较另审链段与顺序证据 | 翻页无漏重；来源行号作稳定排序键不等于证明业务时间顺序 |
| W15 | 注册信息、绑卡记录、交易明细是不同材料；人数、账号数、记录数也不同 | 先识别材料类型，计数标明对象和唯一口径 | 非交易材料不虚构流水；文件数、逻辑记录数、交易数不混叫“笔数” |
| W16 | 方法名字和程序实际执行曾出现不一致 | 输出可追查规则版本、解析器版本与实际适用范围 | 规则卡、程序、回执一致；FIFO、分层追踪等留到专门分析阶段 |

这些经验中，“保真、可追溯、不猜未知”与既有设计一致；账户归一、交易状态模型、跨文件口径处理等新增或未定部分只形成建议，实施前仍需审核与用户确认。

## 4. 第一步：真实样本清单与格式规则卡

### 4.1 清点范围与身份

先清点原 G0 约定的真实角色：同一主案件的建行 XLSX、微信 TXT、支付宝账户明细 CSV、支付宝余额明细 CSV，以及独立案件的冲回材料。它们是三渠道、至少四个具体结构角色，不是看到三个文件后缀就算齐了。

从已找到的工作区核实原件所在位置及版本，建立副本清单。历史微信 5635、支付宝 607/397 等数字只作为定位线索，本轮没有复核，不能写入已确认数据。

每份清单至少包含：

- 稳定代号、案件引用、原件/副本/转换件/加工件身份、上游出处、文件名、字节数、SHA256、来源渠道与材料类型。
- 账户标识及类型、材料覆盖时间、文件版本和补充关系；未知明确记录，不从文件名或同名人员猜补。
- TXT/CSV 的逐文件编码、BOM、分隔符、引号与换行结构；严格解码，不以替换字符掩盖解码失败。CSV/TXT 采用逻辑记录号，物理行数另作观察。
- XLSX 的 sheet、表头、合并单元格、空行、说明和合计、单元格值类型、日期系统、公式及缓存值等观察；不以显示值代替存储事实。解析库要选型、锁版并验证低内存能力。
- 数据/表头/尾部/其他记录计数及独立坐标索引；无法分类的行进入问题表，不直接跳过。

遇加密、缺文件、原件与加工件混淆、版本冲突或无法解释的结构时，登记影响并询问用户；不猜密码、不把现有整理表自动升级为原件。只读原件，在私有目录处理副本。

### 4.2 每个具体结构一张规则卡

| 规则部分 | 必须说明的内容 |
|---|---|
| 识别与适用范围 | `format_key`、结构指纹、材料类型、样本版本；匹配与拒绝条件，不能只按平台名或扩展名识别 |
| 原始抽取 | 数据区、非数据行、字段位置、双列、原始类型、来源坐标；表头重复和合计的明确识别依据 |
| 金额与方向 | A～F、元/分倍率、十进制语法、舍入、方向词表、负号/冲回、双列冲突、零值与未知政策 |
| 币种，单列一节 | 原始 ISO 优先；缺值的 `verified_cny` 证据；“人民币/156”等映射逐项列原文、标准代码、依据并随规则批准；不把其他格式映射借来使用 |
| 时间与身份 | 本地时间精度；区间、时区/缩写与尾注的待核规则；账户来源和标识类型，缺失或原文已失真怎样表示 |
| 交易业务状态 | 成功、失败、撤销、可退款、未知等原词；哪些属于交易记录、是否计入业务汇总。不能拿记录 `confirmed/pending` 代替该口径 |
| 材料视角与余额 | 交易视角/资金变动视角、本方方向、镜像；余额 asset_ledger/debt/available/unknown 及同文件不同业务类型的适用范围 |
| 证据与批准 | 原件代号、坐标、依据、未决问题、`rule_version`、批准记录；规则变化新增版本，不覆盖冻结版本 |

若实践经验与 `docs/02` 冲突，先给出原件反例、影响范围和候选方案，由用户决定是否改规则；不能直接把某案局部处理推广成全银行政策。规则卡中的币种映射单独列出审核结论；沿用当前规则级批准字段，不暗自新增另一套审批系统。

现有 G0 每份 source 绑定一条规则，且逐行 `expected.balance_scope` 必须等于该规则的 `balance_scope`，**尚不能直接表达同文件逐业务类型的不同口径**。若真实盘点发现这种情况，先列问题：由用户决定是否整份按 unknown 保守保留、暂不验链，或另行审核扩展规则/契约及生产存储。保留原始余额与业务类型，不为通过 G0 把某些行强写成可比资产余额，也不能未经批准放宽当前校验。

### 4.3 如何选首个格式

在清单后输出对比：原件可得性、结构稳定度、金额规则证据、异常种类、编码/读取复杂度、可独立产生答案、对实际使用的价值。给出推荐及理由，由用户决定。格式的边界要具体到结构版本，例如“某版微信交易记录 TXT”，不能承诺支持所有微信账单。

## 5. 第二步：把真实 G0 冻结成验收基准

沿用 [G0 契约](09-G0验收契约与核对工具.md)和[当前时间/币种规则](12-G0时间尾注与缩写识别修复.md)，产出清单、规则卡、独立原始索引、A 层答案、B 层裁决、抽查与问题决定，以及固定哈希的正式报告。

1. **独立索引**只确定真实坐标与数据/非数据分类；独立答案生成器按已批准规则产生机械答案。二者实现及输出固定哈希，不调用未来产品金额引擎或解析器生成“正确答案”。
2. **A 层**覆盖可机械判定的普通行；每份含 A 层材料按格式与风险抽查。工具要求至少一次只是最低门槛，实际抽查方案先列清楚；建议包含首尾、不同业务类型和随机普通行。
3. **B 层**覆盖异常与边界，强制筛查冲回、零值、缺字段、双列冲突、非标准时间、余额不可比等；不能只收生成器自称“不确定”的行。每行写依据并由用户或其指定审核人批准。
4. **未知是合法答案**。问题可决定为“依据不足，保持 pending”；不能为了关闭问题而补造时间、金额或账户。
5. **41 项矩阵逐项核对真实见证条件**，合成边界补足难以从真实材料取得的情况，但不能替代必需真实角色与独立案件的已裁决冲回行。
6. 新建数据集版本并保存独立的 bundle 预期 SHA256，再运行正式 `--release`；保存工具、schema、矩阵、索引、生成器、答案与报告版本。

退出条件是正式工具检查通过，且规则证据、人工裁决和独立性经审核认可。`ok=true` 的草稿或合成夹具通过，不等于真实 G0 完成；`ready_for_m1=true` 也不替代业务正确性审核。

**本方案保留完整 G0 门禁。** 用户已授权调整为单格式技术预览，但单格式子集不能宣称完整 G0 或 `ready_for_m1`；完整正式 gate 不变。通用底座可先用合成数据验证；真实格式仍须有独立坐标、规则证据、批准与冻结的子集基准，不能用合成通过证明真实金额正确。预览 UI、回执与版本说明须清楚列出支持格式、只读待核及完整 G0 未完成的边界。

原 `docs/03 §5` 中“每行人工逐笔确认”的旧表述，应在实施定稿时同步为现行 A 层机械生成与抽查、B 层逐条批准，不要求人工重复签几千行。此处只是登记需同步的旧计划文字，不改变当前门禁。

## 6. 第三步：金额引擎与生产存储补齐

### 6.1 先补数据契约，再让解析器写库

| 目前落差 | 实施前需要定稿的设计 |
|---|---|
| G0 规则有方向/币种映射、负号与零值政策，当前 `format_rule` 未完整承载可执行配置 | 规则配置的结构、类型约束、冻结范围、版本读取与迁移；证据文本不能代替可执行配置 |
| `fund_flow` 未完整保存双列原文、原始币种与完整原始记录 | 完整原始载体、原始类型与标准列的关系、不可变保护、来源定位；不只补一个合成金额字符串 |
| 账户类型、平台业务状态和材料视角的保留尚不完整 | 先明确首格式必需的信息及其存储/显示方式；复杂主体关系另列后续，不按姓名归并 |
| 当前单规则余额口径无法完整表达文件内业务类型差异 | 先决定保守文件级 unknown 或单独扩展契约；若扩展，明确逐行适用性如何保存并投影到余额结果，不能只改答案 |
| SQLite INTEGER 到 JavaScript/IPC/界面的精度路径未完成生产验证 | int64 使用 BigInt/十进制整数字符串无损传输；计数与金额分开；禁止隐式转为失真 Number |
| 批次表已有枚举，实际任务、恢复和回执尚无业务服务 | 定义每阶段进入/退出条件、错误码、计数、取消原因、未发布数据可见性和重启恢复 |

采用新增迁移和迁移前备份，验证旧 0.1.4 工作区与案件数据保持可用；不能直接拿提取 DDL 覆盖旧库。G0 schema v3 与 SQLite `user_version` 是两套版本体系，后者按真实存储变更单独定版本。

### 6.2 金额引擎的职责

输入是原始金额/双列、方向、币种、时间、余额等证据及冻结的具体格式规则。输出标准整数分、方向、可知的字段、独立待核原因和判定依据；原文不改写。

先判方向和负号语义，再按元/分倍率与批准的舍入规则处理十进制文本，不经浮点乘法。金额 null 不变零；已知金额但缺时间的行保留已知值并继续 pending。币种默认值不能当识别证据；首版沿用用户已定的人民币边界，外币明确提示且不混入合计，发布策略见第 10 节。

逐行与独立 G0 答案比较金额、方向、币种、时间、账户、冲回、状态和逐项原因。余额值与口径也要保真；余额链计算、人工接受与完整历史仍按原 M3 单独验收，不能用“当前展示了余额”宣告已经完成。

## 7. 第四步：一个格式的解析、归档与批次导入

建议数据流：

```mermaid
flowchart LR
  A[选择真实文件] --> B[核对结构与冻结规则]
  B --> C[归档副本与身份复验]
  C --> D[worker 解析原始记录]
  D --> E[金额引擎与待核原因]
  E --> F[分块写入未发布批次]
  F --> G[完整核对并原子发布]
  G --> H[真实列表 待核 来源与回执]
```

### 7.1 解析边界

解析器处理具体格式的记录边界、字段抽取与来源坐标；金额引擎处理业务判定。两者都保留 parser/rule 版本，不能把银行负号政策藏在通用 CSV 读取函数中。

说明、表头、合计可以按已批准识别规则排除并分别计数；能完整定位和保留的行级业务问题可形成 pending。无法完整保留/定位交易、解码失败、未知结构等按用户批准的文件级策略处理，不以“跳过错误行”冒充完整成功。加密文件给出明确回执，不能只报 0 笔成功。

### 7.2 新文件与范围事务

先通过专门规则登记流程保存冻结版本。单 worker 中为新材料确定 `source_file.id`，声明 `sourceFileIds` 范围，再在该同步范围事务内登记 source、批次和相应记录；新 source 可在事务内创建，并非一定要先存在于库中。现有例子见 [范围事务检查](../code/desktop/checks/hardening.check.cjs)。

解析、哈希与文件复制放在事务外，分块数据库写入使用短事务；不能在同步事务回调里 `await` 文件操作。正常导入复用材料范围增量统计，不每次全案扫描；专用完整性检查/修复另走相应入口。规则不能借材料范围写入一起修改。

### 7.3 归档与发布是两种原子边界

文件系统复制不是 SQLite 事务的一部分。实施设计须包含临时副本、最终归档路径、复制前后大小与哈希核对、从归档字节解析、恢复记录和重启清理；若所选文件在读取中变化，不能把前一份哈希与后一份内容混在一起。

归档完成且身份一致、全部需保留记录入库、坐标与计数核对成功、原因与状态一致后，才在同一数据库事务中标记 done 并切 `current_batch_id`。失败、取消、崩溃或磁盘满不能发布半批；文件系统残留可识别可清理，不能假称复制和入库天然同时成功。

### 7.4 重复与再导

同案同 SHA256 识别为已登记材料，提示已有结果；用户选择跳过或明确新批次重导。每次运行一文件一批，新批次完成前旧 current 继续有效，失败保持旧结果，成功后只统计新的当前批次，旧批次留存可追查。

这不等于跨文件交易去重。两个不同文件出现相同交易号或同秒同额，首导保持来源记录，后续如要交易配对/去重，另定规则与验收。

## 8. 第五步：EXE 中怎样才算“真正可用”

首个交付建议至少包括以下结果，最终范围由用户确认：

1. 当前案选文件，识别具体格式/规则版本，显示文件身份及重复情况，开始真实后台任务。
2. 进度反映真实阶段与计数；失败/取消有原因，成功有文件级回执。回执分别列原始数据记录、非数据记录、已确认、待核及无法量化数量，说明归档和有效批次。
3. 材料列表与流水列表读取 SQLite 真实数据，支持稳定分页和约定范围内的查询；同秒记录与 null 时间有固定显示次序，切案不串数据。
4. 标明“已确认收进/付出”的统计范围与待核数；不把它直接命名为经济收入、成本或诈骗损失。多材料/多账户/重叠视角不具备可加条件时，不展示未经定义的全案净额。
5. 记录详情显示原始字段、标准结果、单位、规则/解析器版本、全部待核原因；首轮人工更正范围见 Q05，不让演示按钮假装已经保存。
6. 基本来源查看能验证归档副本身份，显示目标 sheet+原始行或 TXT/CSV 逻辑记录及上下文；缺失/损坏/同名替换明确失败。只展示一个字符串坐标不算完成来源查看。
7. 关闭 EXE 再启动，案件、材料、当前批次、流水、待核与来源一致；重复导入不重复计数，重导失败仍能查询旧结果。

这是首次真实导入的使用路径，不包含自动跨文件抵消/去重、FIFO、资金追踪、关系图谱、AI/OCR、司法报告或正式导出。完整人工复核、余额链与正式 M4 回源/导出按原计划保留；若首轮只允许查看待核，应在产品中明确，并由用户先批准该交付范围。

验收至少覆盖：

- **完整性**：逐文件独立坐标集合一致，重复交易号以多重记录核对；数据与非数据分类完整，不能只验总数相同。
- **业务值**：逐行标准字段与独立答案一致，核对原始值保真、零与未知、单位、符号、双列、舍入、币种映射、时间边界和全部待核原因；汇总按明确范围复算。
- **版本**：来源哈希、来源坐标、规则与解析器版本、批次均可追查；翻页或保存遇有效版本变化不混用旧上下文。
- **恢复**：空/坏/加密/未知文件、解码错误、归档身份变化、取消、worker 退出、程序崩溃、磁盘满；新文件不暴露半批，重导不损坏旧 current。
- **桌面**：真实 EXE 首导、重启、重复/重导、待核与来源错误路径；开发态通过不能替代打包运行证据。原有回归保持通过，有必要的新测试针对业务不变量与失败结果。
- **规模**：原 M2 的 19.6 万行级样本、worker 峰值 RSS<1GB、点击/滚动响应<200ms 和耗时基线仍要实测。历史加工件可作规模输入，不因此成为业务答案原件；大样本未过时明确交付限制，不能宣布完整 M2 完成。
- **完整 M4**：随机至少 200 行及全部异常行的回源、Excel 边界与 235 万行合成导出继续保留，首次来源查看通过不替代这些最终验收。

以上是完整验收要求。方案初稿阶段没有执行；后续实施中实际完成了哪些检查，以实施交付文档及对应证据为准，不把尚未执行的规模、真实业务批准或打包验收算作完成。
