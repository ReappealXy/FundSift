# 首个可用导入方案：交叉复核意见（供用户与 Codex 审核）

日期：2026-11-18。复核对象：[docs/13 实施方案](13-真实样本与首个可用导入实施方案-待审核.md)。本文只读代码、契约与 WorkBuddy 本地材料，**未修改产品代码、数据库或安装包**。

## 1. 结论

方案可以批准开工，分层、原子边界、A/B 层与“不放松门禁”的立场都对。但有 **5 个 P0 落差**必须在写解析器之前落到迁移里，否则“导入成功”会建立在错误默认值和不足的原文载体上；另有 4 条建议与 6 条 WorkBuddy 补充经验。建议按“P1 盘点与 P3 存储/引擎并行、P2 子集基准、P4/P5 单格式交付”的顺序推进，并把首个 EXE 明确标为技术预览。

## 3. P0：写解析器之前必须定稿

1. **`fund_flow.currency TEXT DEFAULT 'CNY'` 与“币种默认值不能当证据”直接冲突。** 迁移应改为可空、默认不写值；只有规则声明 `verified_cny` 或原始 ISO/已批准映射命中时才写 CNY。合计按币种分组，`null` 不进入任何合计。
2. **原文载体不足。** 至少补 `raw_income_text`、`raw_expense_text`（D 类双列）、`raw_currency_text`、`raw_record`（整行原文或规范化 JSON），并明确它们只增不改。完整原文以归档原件为权威载体；库内 `raw_record` 存指针/摘要即可，确需内联时超限要显式失败或转存，不做静默截断。
3. **规则可执行配置没有落点。** 建议新增 `format_rule_config`（JSON + 内容哈希 + 批准人/时间 + 冻结标记），或扩展 `format_rule` 列；无论哪种，都必须满足：不可原地改版、旧批次读旧版本、G0 规则卡与库内配置逐字段对应。
4. **归档清单缺表。** `source_file.file_path` 只记录最终位置，无法表达“复制前哈希、复制后哈希、临时文件、清理状态”。建议 `archive_entry(batch_id, relative_path, sha256, bytes, staged_at, status)`，启动时做幂等清理；复制前后各算一次哈希，不一致直接失败。
5. **稳定排序与索引缺失。** 列表分页必须固定为 `(txn_time IS NULL, txn_time, source_file_id, source_loc, id)` 一类的全序，并建对应索引；索引只解决速度，分页令牌还要绑定案件 `case_data_state.data_version`、筛选与排序条件。人工修改或解除待核也会改变数据，版本不一致时首版直接提示刷新，不做“旧快照继续读”。

## 4. P1：建议补进方案

- `import_batch` 增加 `pending_rows`、`unquantifiable_rows`、`error_code`、`cancel_reason`；回执与 UI 用同一组数字。
- `source_file` 增加 `perspective`（本方/对方/镜像）、`declared_coverage`（时间范围）、`encoding`/`bom`、`header/footer/data` 计数；与样本清单字段一一对应。
- 进度协议增加真实计数（已解析/已写入/待核），不要用假百分比；取消语义按阶段列表化（归档前/归档后未发布/发布中）。
- UI 明确空态、加载态、失败态；待核原因支持多条并逐条显示原因码与说明；合计标签写清“已确认收进/付出，按币种”，未知币种或待核时显示“不计算/未覆盖”及数量，不用 0 代替。

## 5. WorkBuddy 经验交叉核对

docs/13 的 W01～W16 与本地私有索引一致，我抽查了私有索引指向的案例 A 记忆文件（具体路径与行号见本地私有索引），确认以下判断有原始依据：

- 支付宝账户明细与余额明细是两种视角、存在重叠、余额明细不能单独用（W10）；
- “不整表求和、镜像两侧不相加、红包用对手方接收金额列、统计前先归一化、银行行逐笔判镜像”是已经踩过坑的五条铁律；
- 交付表把“来源文件/来源工作表/来源行号”和“原始值 vs 归一值”做成显式列（W02/W08）。

据此建议再补 6 条（编号接 W17）：

| 编号 | 经验 | 融入设计 | 验收 |
|---|---|---|---|
| W17 | 原文与标准值并排，差异需能解释来源 | 列表提供“原文≠标准”筛选，同时显示差异来源（单位换算/币种映射/符号规则/人工修改）；人工修改走独立审计记录 | 规则产生的差异不被当成人工改动，人工改动可追到人和时间 |

## 6. 施工顺序建议

P2 的“完整 G0”依赖全部真实角色与独立案件的冲回材料，容易把 P3/P4 一起卡住。建议：

1. **P1 先行**：清单、哈希、结构观察、账户覆盖矩阵、首格式对比；
2. **P3a 并行**：与格式无关的存储迁移、原文载体、金额引擎、int64 通路——不需要真实答案即可做，用合成夹具验收；
3. **P2 子集基准**：只为选定格式建立“该格式行级 + 相关边界”的冻结基准，明确标注“子集”，不宣称 `ready_for_m1`；
4. **P4**：只接这一个格式；
5. **P5**：EXE 标“技术预览”，完整 G0 与其余格式仍按 M1～M4 验收。

## 7. 首个格式建议

按“结构风险从低到高”排序，供 P1 盘点后确认：

1. **支付宝账户明细 CSV**：行数最少、单视角、无合并单元格、无余额链；
2. **微信 TXT**：行数多、需处理编码与红包列（W19）；
3. **建行 XLSX**：合并单元格、公式、表头多层，解析风险最高，建议最后。

## 8. 验收补充（负向）

空/坏/加密文件；归档后文件被替换；复制中途磁盘满；worker 被 kill；发布前取消；重复导入同一文件；旧 current 仍可查；规则版本变更后旧批次显示旧版本；`currency=null` 时合计显示“未覆盖”而不是 0；同秒与 null 时间翻页无漏重；翻页中途人工修改触发版本提示。

## 9. 需要用户拍板

1. 是否接受“技术预览”式的单格式交付（完整 G0 仍是 M 级门禁）；
2. 首个格式选哪一个（建议支付宝账户明细，以 P1 为准）；
3. `currency` 迁移策略：改为可空 + 规则声明，还是保留默认值但在导入层强制校验（建议前者）。
