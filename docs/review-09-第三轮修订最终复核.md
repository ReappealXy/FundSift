## 二、仍需补的两处

### 1. [高，M1前] 已验证状态没有强制进入冻结状态

位置：[02:111](D:/Analyze/FundSift/docs/02-金额符号处理规则.md:111)、[02:113](D:/Analyze/FundSift/docs/02-金额符号处理规则.md:113)、[03:68](D:/Analyze/FundSift/docs/03-第一片开发计划-并表闭环.md:68)、[03:171](D:/Analyze/FundSift/docs/03-第一片开发计划-并表闭环.md:171)。

文档规定verified≥1后不可改，当前触发器却只检查OLD.frozen=1；verified和frozen之间没有约束或自动转换。

实际复现：

~~~sql
-- 新规则最初未验证、未冻结
UPDATE format_rule SET verified=1 WHERE id=1;
-- 查询得到 verified=1, frozen=0

UPDATE format_rule SET amount_expr='B' WHERE id=1;
-- 仍可成功修改
~~~

直接INSERT verified=1、frozen=0也可成功。现有探针先手工写verified=1、frozen=1，只验证了“已经正确冻结后能挡更新”，没有验证“验证通过时必定冻结”。

**最小修法：** 强制verified≥1蕴含frozen=1。例如增加CHECK，要求验证动作在同一次UPDATE中同时设置verified和frozen；或用触发器保证该转换。具体实现可自行选择，但不能只靠调用者记得设置。

补充探针：
- INSERT verified=1、frozen=0应被拒绝或自动冻结；
- 从未验证状态更新verified≥1后，应处于冻结状态；
- 随后修改金额规则、修改原单位/倍率、尝试解冻均被拒绝；
- 新增另一个规则版本仍可执行。

这项可在M0建库阶段补齐，不需要推翻目前表结构或再导方案。

### 2. [中，M0探针] 探针失败仍以成功退出，可能误报通过

位置：[ddl_probe.py:12](D:/Analyze/FundSift/code/ddl_probe.py:12)、[ddl_probe.py:65](D:/Analyze/FundSift/code/ddl_probe.py:65)。

probe函数遇到“本应拒绝但实际允许”“本应允许却被拦截”或其他异常，只打印文字，没有累计失败；脚本最后无条件输出成功结论，并以退出码0结束。

本轮在内存中移除冻结触发器，保持磁盘文件不变，执行同一探针逻辑：
- 第3项输出“frozen UPDATE：可执行 !!不该被允许”；
- 退出码仍为0；
- 末尾仍打印“R3触发器生效”。

因此不能仅用“进程成功退出”作为M0的探针通过依据。

**最小修法：** 每项对照预期记录pass/fail；任何非预期结果均累加失败，最后有失败就以非零状态退出，只有全通过才打印成功结论。最好比较具体异常/约束类型，避免把其他IntegrityError错当成预期拦截。

当前SQL副本与文档完全相同，不存在本轮测试错版本的问题。为了以后复跑仍核验最新设计，可直接从文档提取SQL，或在脚本启动时校验副本与文档SQL一致，发现漂移即失败。
