### 案件统计方法

案件根目录采用递归文件数和字节和；显式跳过 Windows Junction，避免递归到外部缓存。CSV 使用 csv.reader 统计逻辑记录，并分别处理 UTF-8-SIG、GB18030。SQLite 以只读 URI 查询表行数。案件A/B根目录实名段已在本报告中脱敏。目录总量依赖统计范围和时间，项目文档应同时记录快照日期、包含/排除目录和字节单位。

## 架构可行性

**结论：Electron + 每案一个 SQLite 文件可支撑百万级单机流水，方案可继续；“千万行无忧”以及“已由两案数据证明”没有足够证据。**

本轮另用 Python 自带 SQLite 在 D:\Analyze 下的临时目录执行 WAL 落盘合成测试，按 50,000 行提交，写入 2,350,000 行、建立 case/time 与账号索引，再做全范围聚合。结果：写入 3.99 秒、建索引 11.14 秒、聚合 0.426 秒、数据库约 333.2 MB。测试数据库随后由临时目录自动清除。它证明 SQLite 对这个形状的数百万行数据可行，不证明 Node/Electron 的端到端时延、真实行宽、磁盘空间峰值或导出速度。

主要技术坑：

- 计划称 SheetJS 流式解析 xlsx，但没有给版本、具体 reader API 或实测峰值。必须验证所选版本能否逐行读取大工作簿；不能把 CSV 流式解析能力外推到 XLSX。案件B约 1.75 GB xlsx 总量也不能代表单个文件大小，需先统计最大单文件并实测。
- Excel 单工作表最多 1,048,576 行。约 235 万条记录不能直接塞入一个表；导出需明确多工作表/多文件拆分、表头、排序和回源列策略。
- better-sqlite3 是同步接口。只把解析放 utilityProcess，仍可能让 Electron 主进程在批量写库、建索引、导出时卡住。数据库批处理也应在 worker/utilityProcess 执行，前端只拿分页和汇总。
- WAL 适合单机并发读、单写场景，不会让多个写入自动并行；需要定义长事务、busy timeout、磁盘不足、异常退出恢复、备份和迁移策略。
- 本轮 22 条 HYJX SQL 的小样执行只验证 SQLite 方言/候选可执行性；AMT_0004 已有引擎差异，不能用作 SQLite 性能或业务正确性背书。
- native better-sqlite3 与 Electron 版本需要锁定并在打包产物上验证 ABI、重建、数据库初始化、WAL 文件关闭与重开。
- 大文件流程还需验证 CSV 引号内换行、编码误判/手工覆盖、XLSX 多工作表/隐藏行/公式单元格、解析中断续跑及部分提交回滚。

## 逻辑漏洞

### 金额符号

1. A/B/C 是 16 个“带绝对值配置”格式的静态分类，不是所有银行、微信、支付宝文件格式的完整分类。至少还要将收支双列作为独立结构（文档的 D 类）处理；D 类是否有某列同时填值、负值、两列皆空或两列皆有值，需要明确冲突规则。文档的 E 类方向列+无符号金额也应与 C 类的条件边界写清。
2. “先判方向→取绝对值→加符号”是可用的处理顺序，不是足够的算法。它只有在格式版本正确、方向来源权威、符号/方向冲突有明确处理时才成立。至少要区分：金额符号决定方向（A）、负金额反转方向字段（B）、方向字段优先（C）、双金额列（D）、方向列+无符号值（E）、零金额/缺字段/冲突值。冲突或未知格式应进待核状态，不能默认为任何方向。
3. unit_scale 目前只写 INTEGER，注释又写“100 分→元记 100”，但标准金额存整数分。需把“来源单位→标准存储单位”的方向、倍率和舍入规则定义唯一；建议金额先按原始十进制字符串精确解析，再按币种存整数最小单位。raw_amount 若只存整数分就不是原始值；另存 raw_amount_text/raw_balance_text 和币种、原单位，才可重现转换。
4. format_rule 的 verified 布尔值不足以表示版本、证据来源、测试样本、审批人、规则修改历史。规则应绑定表头/结构指纹和平台格式版本，并记录每次转换使用的规则版本，避免以后修改规则造成旧数据无法解释。
5. 对真实案件里所列的退款/冲正和平台金额样例，本次没有获准读取内容，因此 docs/02 的实证不能作为已验收的测试用例。应整理去标识化、留有原行坐标的样本和逐行预期结果。

### 余额链

文档坚持不因余额不平自动翻转方向是正确的保护措施，但当前公式和字段仍不够：

- “上一笔余额+本笔标准金额=本笔余额”要求同一账户、币种、余额口径、完整流水段和正确顺序。时间相同需稳定次序；多文件时间重叠、倒序导出、缺行、手续费、冻结/可用余额、信用卡欠款口径均可能使公式不适用。
- 标准资金流方向不一定等于账户余额变化方向。信用账户、退款、代扣等情况应分别保存资金流金额和账面余额差额/余额口径，不能默认都用 amount 做余额差。
- fund_flow.balance_ok 每行只有一个标记，不能解释比较了哪两行、差额多少、为什么不平、采用哪个排序/规则，也无法表达“无前项/跨文件断点/余额类型不匹配”。建议增加 balance_check 结果记录：账户与余额口径、前后行 ID、计算差额、差异金额、规则版本、异常原因和人工处理状态；只对可比连续区间给出通过/异常。

## 第一片计划问题

### 表设计缺项

- case_info、source_file、fund_flow、format_rule、import_check 的外键、非空约束、唯一约束和状态枚举没有定义。source_file.file_sha256 只有普通索引，无法落实重复导入规则；需明确同案件、同哈希、同解析规则的重复文件如何提示、重导或强制再导。
- source_file.file_path 依赖原路径持续存在。审计回源应保留原始文件副本或受控归档定位、原文件名、大小、SHA-256、导入批次和解析器版本。
- source_row_no 不足以定位 xlsx：至少还需 sheet 名、工作表行号、数据记录序号；CSV 应保存逻辑记录号，而不是简单物理行号。fund_flow 还应保留原始单元格/字段值或原始行快照，以支持复核和复现。
- fund_flow 缺 currency、原金额字符串/原单位、余额类型、来源格式版本/指纹、规则版本、交易流水号/订单号等可用字段。当前 raw_amount INTEGER 注释为整数分，无法完整还原“原始金额”。
- format_rule 缺结构指纹、版本号、规则明细/优先级、来源与验证记录、批准时间；platform/format_key 未设唯一组合。
- import_check 混合行数、余额、符号、重复等异质结果，ref_rows JSON 也没有约束。还缺运行批次、错误代码、预期/实际值、影响金额、复核状态/处理记录。建议将导入运行记录与余额/符号/重复检查结果分层保存。
- created_at 等时间字段未定义时区；txn_time TEXT 应同时保存原始时间文本、时区/精度和规范化时间，避免跨时区或同秒流水排序不稳定。

### 里程碑验收缺口

- M1 的“用 docs/02 实证用例单测”没有随项目交付的去标识样本、精确输入、期望方向/分值和测试数据许可证；且其中若干案件样例本轮未能核验。
- M2 的“不爆内存”没有最大内存、完成时间、磁盘峰值、取消/失败恢复和部分导入回滚阈值。19.6 万行文件来自交付结果目录，不能证明导入器已处理同一原始文件。
- M3 的“与手工并表逐笔对照”未规定行序、重复行、金额容差、同秒记录和余额口径；应交付固定的黄金样本和可机器比较的结果。
- M4 只写“导出可用、任意行可定位”，未规定超过 Excel 单表上限时如何拆分，也未规定导出记录数、字段完整性、哈希/规则版本和回源成功率。
- M0 双击启动和重启不丢数据还应在最终安装包上测，而不只在开发环境。
- 第一片建议补：导入批次状态机、断点续跑/失败回滚、格式不识别待确认、同文件重复与规则变更重导、备份恢复和数据库迁移、导入/导出期间进度与取消、磁盘剩余空间检查。

## 风险清单

| 等级 | 风险 | 影响 | 必须的缓解 |
|---|---|---|---|
| 高 | 金额符号、单位或方向规则错误/冲突时仍自动标准化 | 并表方向及汇总金额直接错误，审计结果不可依赖 | 规则版本化；保存原值；未知/冲突待核；按去标识样本逐格式验收 |
| 高 | 溯源锚点只有路径和行号 | 文件移动、工作表/多行 CSV 后无法定位到原证据 | 原件归档或受控引用；哈希；sheet/逻辑记录坐标；保留原始行 |
| 高 | XLSX“流式”能力和 Excel 行数上限未验收 | 大文件卡死/内存耗尽，或导出结果无法覆盖全部记录 | 锁定解析库版本和 API；以最大真实单文件压测；实现并验收拆表/拆文件 |
| 高 | 余额链把资金流方向等同账面余额变化 | 信用账户、余额类型混用和跨文件拼接产生误报/漏报 | 明确账户与余额口径；存前后行、差额和原因；只校验可比连续段 |
| 中 | 同步数据库操作占用 Electron 主进程 | 导入/索引/导出期间界面冻结 | 数据库与解析批处理放 worker/utilityProcess；分页通信；压测长任务 |
| 中 | 规则模板只用平台/格式名，没有版本指纹和审批记录 | 新旧格式误匹配，规则更新后旧结果不可解释 | 结构指纹+规则版本+验证记录；未识别格式进入待确认 |
| 中 | 失败重试、原子提交、重复导入口径不明确 | 产生半批数据、重复行或误拒绝合法重导 | 导入批次状态机、事务边界、唯一策略和恢复测试 |
| 中 | 以工作区总量代表原始流水规模 | 压测样本和项目承诺失真 | 记录原始/中间/交付分层的快照、字节口径、CSV逻辑记录和去重范围 |
| 低 | SQLite/Excel/打包版本未锁定，索引和迁移策略未量化 | 依赖升级或数据增加后出现性能、兼容问题 | 锁版本；维护迁移脚本；打包冒烟；用真实代表性查询压测 |

## 最终判定：需修改

可以保留 Electron + SQLite 单机方向并进入骨架准备；并表核心编码前先完成以下修改：

1. 写清 A–E 及双列、零值、负值、缺字段和方向冲突的决策表，明确单位换算及舍入；保留原金额文本和转换规则版本。
2. 修订 source_file/fund_flow/format_rule/import_check 溯源字段、唯一键、外键、批次和规则版本；xlsx、CSV 回源坐标可逐行定位。
3. 重新定义余额校验适用条件和结果数据结构，分离标准资金流方向与余额变化。
4. 锁定 XLSX 解析实现和版本；验证最大单文件；规定超百万行导出拆分方式及 Excel 回源列。
5. 为三个打样格式准备去标识黄金样本，列出每行期望值；把内存、耗时、失败恢复、导入重复、导出完整性和回源成功率写成量化验收值。
6. 把案件规模标成有日期和目录边界的快照；分开原始输入、加工件、交付件与版本库，避免把副本行数当作独立原始交易数。
7. 把规则执行和数据库批处理放在不会冻结界面的进程，并验证打包产物、异常重启、备份恢复和迁移。
