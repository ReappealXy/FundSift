## 1. 本文要解决什么

M0 已交付案件创建、工作区选择、案件切换与重启保存。本次拟补的是正式业务写入口上线前的数据保护、版本升级和统计口径，不把真实流水解析、金额引擎、人工复核或正式导出写成已经完成。

修订后的主要方向：

1. 先定义工作区库、案件库各自的版本升级与失败处理，再添加约束。
2. 优先用触发器和索引加固已有结构，不预定必须重建表或在下一版改为 STRICT。
3. 保持 current 为有效批次的唯一依据，损坏时明确报异常，不自动猜测历史批次。
4. 共性数据检查覆盖所有规则等级；规则语义检查同时覆盖样本验证与人工确认。
5. 列表读案件级统计摘要，明确摘要失效、事务更新及数据版本。
6. 保留合法待核记录，发布前拒绝的是违反不变量的数据，不是所有 pending 数据。

## 3. 版本升级方案

### 3.1 版本与兼容边界

- 拟定义独立的工作区 schema 版本与案件 schema 版本；本次目标分别为 v2，不再依赖一个常量假定两者永远同步。
- 已知 v1 只走明确的 v1→v2 路径；v2 重开不重复升级。未知结构、未知 application_id、未来版本均拒绝写入。
- 新建 v2 与 v1 升级后的业务表、触发器、索引及桌面辅助结构应等价，不能出现“新案有保护，旧案无保护”。
- 已有案件即使流水为零，也保留名称、编号、UUID 和目录身份。不能据未找到某个配置文件就认定没有任何需要保留的案件。

### 3.2 单库升级步骤

1. 暂停该库业务操作，验证文件位置、application_id、版本、已知 v1 结构与案件身份。升级所需的数据库读写在数据 worker 执行。
2. 预检查旧数据：金额类型、符号、confirmed 空值、原因与状态、案件/文件/批次关系、有效指针，以及工作区编号的 NOCASE 冲突。
3. 使用 SQLite 一致性备份能力生成独立备份，记录源版本、身份与检查结果；回读备份核对身份、关键行数、外键及完整性。不能只复制主 `.sqlite` 文件，遗漏 WAL 中已提交的数据。
4. 取得升级所需写锁后，在同一事务内重新核对前置条件，添加触发器、索引与辅助表，初始化摘要并执行升级后检查。备份期间或取锁前若源库发生变化，停止并重新备份，不使用过期备份继续。
5. 所有检查通过后，在同一事务内写入目标 `user_version`，再提交；创建对象、初始化数据和版本号不能分成可见的半升级状态。
6. 提交前失败则回滚，保留备份和清晰错误，原有业务值不变；提交后进程异常，重启识别完整 v2，不重复执行 v1 步骤。

已有违规记录或编号冲突时停止升级并报告，不自动改金额、舍入、翻方向、删除记录、改案号或合并案件。新增触发器不会追溯检查旧行，所以第 2 步不能省略。

### 3.3 两类库不宣称共同原子升级

工作区索引与每案数据库分属不同文件。工作区已是 v2、部分案件仍是 v1，是需要处理的中间状态，不能称为全工作区单事务。

拟支持逐案识别、可重试升级：某案失败时，该案标明升级未完成/暂不可用，其他已验证兼容的案件可用；不创建空案替代。后续再次打开失败案件时重试明确的升级流程。

备份按库记录升级前后版本与身份。失败回滚和提交后恢复备份是两件事：后者可能丢弃升级后新增业务，不能静默执行，更不能只替换一个库就声称全工作区已恢复一致。

## 4. 数据保护的拟实现要求

### 4.1 金额、方向与类型

| 条件 | 处理 |
|---|---|
| `amount` 非空 | 必须实际存为 SQLite integer，不能是 real 或无法转换的 text；INTEGER 亲和性不等于严格整数约束 |
| `amount` 为空 | 只允许 pending，原始值和具体原因仍保留 |
| `amount > 0` | 标准方向必须是“进”，NULL 也拒绝 |
| `amount < 0` | 标准方向必须是“出”，NULL 也拒绝 |
| 方向尚不可确定 | 不制造带符号标准金额；保留原始字段，标准金额可空并待核 |
| `amount = 0` | 整数零可保存；是否可确认、方向如何记录，按已验证格式规则与黄金样本决定，不能从正负号猜测 |
| 零值规则未定义 | pending，建议原因代码 `amount_zero_rule_undefined`；该代码名随 M1 原因词表审查定稿 |

`100.0` 或文本 `'100'` 经亲和性转为 integer 后，数据库类型检查可能允许；写入口还须负责从原始十进制字符串精确解析、元分换算和范围检查。数据库 integer 检查不证明来源金额语义正确，也不代替 JavaScript/IPC 精度处理。

触发器须覆盖 INSERT、UPDATE，以及通过 REPLACE/UPSERT 进入的写入路径，不能只检查首次 INSERT。判错不能简单写 `WHEN NOT(valid_expr)`，因为 NULL 可能使触发器不执行；可以使用明确的 `IS NULL`、`IS NOT` 或 `valid_expr IS NOT TRUE`。

例如，以下只是非零方向的判错条件示意，不是完整升级 SQL：

```sql
-- IS NOT 在方向为空时也能得到明确的判错结果。
(NEW.amount > 0 AND NEW.direction IS NOT '进')
OR (NEW.amount < 0 AND NEW.direction IS NOT '出')
```

不能把示意条件当作完整金额引擎：类型、空金额状态、零值规则、关键字段与原因聚合仍须分别检查。

### 4.2 案件、文件、批次归属

写入和修改时均验证：

- `import_batch.case_id` 与其 `source_file.case_id` 一致。
- `fund_flow` 的 case/file 与所引用 batch 绑定一致。
- 非空 current 指针必须指向存在的、本案本文件、done 的批次；first 指针也须与本案本文件匹配，不能借另一文件的批次充当首次运行。
- 不能先写合法流水，再通过修改父行破坏关系。保护范围包括 batch 的 case/file、source 的 case、current 指针，以及被 current 引用批次的 done→failed 等变更。
- 对已登记并被使用的案件、文件、批次身份，优先禁止原地改写；导入重试新建批次，不复用旧批次换身份。数据库约束需覆盖 UPDATE、删除/替换等会使既有引用失效的路径。

打开时检查是发现既有损坏的补充，不代替写入保护。库层允许手工构造错配，不等于当前桌面界面已经串案；本次加固关闭的是这种结构缺口。

### 4.3 案件 UUID 辅助身份

新建案允许初始化唯一 `id=1` 身份，初始化后拒绝 UPDATE、DELETE、同身份位置的再次 INSERT/REPLACE，以及 UPSERT 改写。不能只依靠 DELETE 触发器阻止 REPLACE；需在插入路径检测身份已存在。

升级前先验证原 UUID 与工作区登记相符，之后再安装保护。`recursive_triggers` 开/关均不能改变保护结论。

### 4.4 状态聚合与规则等级

- `fund_flow.status` 是整行状态；未解除的金额、时间、账户等阻断原因分别保留。余额 fail/manual 不自动改变交易金额或整行状态。
- 原因、标准字段和聚合状态由 worker 在同一事务内维护。不能把跨表最终一致要求写成每条中间 SQL 都必须满足，否则会把合法的“先建 pending 行、再登记原因”流程卡住。
- 发布前验证所有原因已登记，聚合状态一致；人工复核只解除一项原因时，其余原因仍有效。基础行内约束在写入时立即生效。
- `done` 表示完整发布，允许含合法 pending 行。应为零的是未解释的数据违规，不是待核记录数。

| verified | 含义 | 检查要求 |
|---|---|---|
| 0 | 未验证 | 基础类型、归属、状态不变量照常检查；未验证语义不能直接产出可靠 confirmed 结果；未知格式整体处置继续按既有设计 |
| 1 | 已样本验证 | 基础检查＋对应规则版本的格式语义检查 |
| 2 | 已人工确认 | 基础检查＋对应规则版本的格式语义检查，同样不得漏检 |

## 5. 有效批次与统计状态

| 场景 | 正式统计与界面 |
|---|---|
| 没有来源文件 | 真实空案，材料和流水为 0 |
| 文件有合法 current→done | 只统计 current 所指批次，不叠加历史批次 |
| 重导失败，旧 current 仍合法 | 保留旧有效结果；另外提示最近一次导入失败/取消 |
| 已登记文件但从未成功发布 | 说明尚无有效结果；不能将失败/未导入冒充“成功导入了 0 条” |
| current 非空但目标失联、归属不符或不是 done | 批次异常，相关总数不可确认为完整结果，不自动选最新 done 替代 |
| current 为空，却已有完成发布的证据或文件状态声称 imported | 状态矛盾，列为异常；不能静默挑历史 done 恢复 |
| 合法 done 批次确实没有交易行 | 可以是真实 0，需有完整解析与非交易行计数依据，不能仅凭空计数认定成功 |

首版建议采取保守显示：案件存在未发布文件、异常指针或摘要不可信时，材料登记数可明确显示，有效流水/待核全案总数显示“—”及原因。已知部分数量若另行展示，必须标“已确认部分”，不能冒充全案完整总数。

正式汇总、并表、复核与导出共同使用同一个有效批次判定。历史数据只作明确的历史参考，不自动进入正式结果。异常修复入口属于单独能力，本轮不默增“自动恢复最新批次”功能。

## 6. 统计摘要与更新时间

### 6.1 摘要放在案件库内

拟新增案件级单行摘要及必要的变化标记，保存案件身份、业务数据版本、摘要对应版本、生成时间、有效性，以及材料数、有效流水数、待核数和文件状态分类。尚无有效结果或摘要失效时，业务总数允许未知，不用 0 填补。

- 列表每案只读身份/版本及摘要，不进行 fund_flow 全量 COUNT/JOIN；整个列表仍是随案件数增长的读取，不承诺 O(1)。
- 摘要与案件业务变化在同一案件数据库事务提交。首版不新增工作区统计镜像，避免额外的跨库同步协议。
- 文件登记、批次状态变化、current 发布/切换、流水标准值/状态变化、待核原因处理等入口都纳入摘要维护。余额变化只有影响摘要中明确包含的字段时才更新相应统计，不能偷偷改变 pending 定义。
- 相关表写入须有轻量失效保护，覆盖遗漏 worker 维护的写入路径；标失效不做每行全案重算。worker 完成业务事务前刷新受影响统计、写入对应版本并恢复有效标志。
- 摘要缺失、身份不符、失效或版本不匹配时显示未知/需检查，不能在列表刷新时自动全案扫描并伪装成廉价读取，也不能把旧快照当即时值。
- 初次升级允许完整计算摘要；之后利用已校验的批次计数/受影响范围维护。具体更新 SQL 和索引须随实现审查，不能仅凭本方案保证性能。

### 6.2 检查分层

| 时机 | 检查范围 |
|---|---|
| 案件列表 | 路径/可读状态、必要身份/版本、摘要有效性；不扫描所有流水 |
| 打开案件 | 身份与版本、摘要/变化标记、文件与批次指针元数据；相关成本仍随文件/批次数变化 |
| 批次发布 | 本批完整行数、字段、规则、原因状态、归属；全部通过后同事务置 done、切 current、更新摘要 |
| 人工复核 | 被修改记录、受影响统计及余额链范围；事务内校验过期提交 |
| 版本迁移/明确完整性检查 | 已有数据全量语义检查、外键、结构完整性及摘要回算比对 |

“发布全量自检”指本次发布批次的全部相关数据，不是每次发布都扫描工作区所有案件历史。`integrity_check=ok` 与外键检查通过不能代替业务不变量检查。

### 6.3 更新时间建议

- “最近更新”表示案件业务数据最后成功变更的时间；创建、材料登记、导入状态变更、有效批次发布、人工复核等实际落库变化按统一规则推进。失败/取消产生了持久化任务状态时属于业务变化；仅弹出一个错误且无业务变更时不推进。
- 单纯打开案件仅更新 `last_opened_at`。运行完整性检查、重算同内容摘要或升级 schema 不伪装成案件业务修改。
- 业务时间以案件库同事务保存的值为准。现有 `workspace_case.updated_at` 若保留，只能作为登记/缓存信息，不能因跨库更新失败让页面显示一个错误的权威时间；列表应读取案件端权威值。
- 历史没有可靠变更时间时保留已知旧值并说明来源，不把升级执行时间填成历史业务更新时间。

## 7. 编号与目录的建议产品规则

以下是待审查、待实施前确认的建议，不能当作用户已经确认或软件已经支持：

| 项目 | 建议 |
|---|---|
| 编号判重 | 保留原始显示，继续 trim；工作区内按 SQLite NOCASE 判重，仅折叠 ASCII A–Z，不折叠 Ä/ä、全半角或标点 |
| 判重一致性 | 查询、数据库唯一索引、错误提示使用同一规则；旧 A1/a1 冲突阻止升级，逐案保留等待用户处理 |
| 首次选目录 | 已有合法工作区按兼容性打开；新建工作区若目录非空，先说明将创建 workspace.sqlite 和 cases/，用户可取消重选 |
| 目录重名/损坏 | 既有索引不兼容、cases 被文件占用、已有案件却丢索引等继续拒绝；不能用一次“确认继续”绕过原有保护 |
| 等待确认期间 | 尚未创建数据库或目录项；用户取消不写入。确认后再次检查目录状态，不能对确认期间的新冲突覆盖写入 |
