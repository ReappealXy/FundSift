## 3. P1：首次导入失败后无法重试

- **复现**：用一条结构损坏的 17 列 CSV 导入，解析期报 `FS_FORMAT_STRUCTURE`；材料状态变为 `failed`，当前批次为空。再次选择**同一文件**，得到 `FS_IMPORT_DUPLICATE`。
- **原因**：[import-service.cjs](../code/desktop/import-service.cjs) 在解析前就登记了 `source_file`，失败后只把批次标 failed；下一次仍按“同案同哈希已登记”拒绝。`desktop-data.cjs` 的 `importFile` 没有 `reimport` 参数，界面也没有“重新导入/重试”入口。
- **影响**：一次临时失败（文件结构、磁盘、权限）会让这份材料永久卡在失败态；用户只能新建案件绕过。预览阶段这属于明显可用性缺陷。
- **建议**：当 `source_file.current_batch_id IS NULL` 或最近批次为 `failed` 时，允许同一哈希重新建批次（旧失败批次保留、不覆盖）；材料页给“重试导入”按钮。若坚持“重复必须显式确认”，至少把 `FS_IMPORT_DUPLICATE` 区分为“已有有效批次”和“仅有失败记录”。

## 4. P1：归档暂存没有清理路径

- `ArchiveStore.cleanupStaging()` 已实现（含引用检查、宽限期、staging-only），但**生产代码没有任何调用**，只有测试调用。
- 归档在复制阶段失败/取消时，会留下 `archive/.staging/*.tmp` 与 journal；`recoverInterruptedImports()` 只列出恢复记录，不清理。预览版没有入口查看或清理这些残留。
- **影响**：磁盘逐步增长；部分副本可能含敏感内容；用户以为“失败就没留下东西”。
- **建议**：案件打开或材料页刷新时，对超过宽限期、无 `archive_entry`/批次引用、且无进行中任务的 staging 做一次清理，并显示“已清理 N 个未完成暂存”。删除门禁必须是事务内实际引用查询，不能只看计数。

## 5. UI/可追溯性改进

1. **1024×720 下主操作被挤出视口**：`.desktop-ledger{min-width:960px}`，内容区约 760px；截图里“查看原文”列完全在右侧视口外，待核原因也在视口边缘被裁。建议最后一列 sticky，或把“查看原文”放到行点击/详情里；原因列加 `title` 或固定宽度换行。
2. **舍入不可见**：截图首行 1.005 元 → -1.01 元、状态“已确认”；舍入证据只存在于详情里折叠的“保存时的处理依据”JSON。建议在详情标准金额旁显示“舍入：1.005 → 1.01（ROUND_HALF_UP）”，或在列表加“舍入”小标记。
3. **材料页显示英文格式键**（`alipay-account-17col-v1`），建议显示“支付宝账户明细 · 17 列”等中文名，格式键留在详情。
4. **回执不显示附加诊断**：微信 3 条 JSON 诊断已存入 `derivation.supplementary_diagnostics`，但回执/材料页只显示待核数。建议回执加“附加诊断 3 条”，详情可展开。
5. **`archive_entry.batch_id` 始终为 NULL**：登记时批次尚未创建，后续也不回填。该列目前是“看起来有用、实际空着”的字段；建议发布时回填，或从表里去掉，避免误用。
6. **规则批准来源是代码常量**：`approvedRule()` 里 `by:'项目规则批准人'`、`at:'2026-11-19'`，与私有 decisions 文件没有可核对的哈希关联。正式冻结前建议把决定文件的哈希/代号写入 `source_evidence` 或规则配置，避免“代码说已批准”。

## 6. WorkBuddy 与 Hindsight 对照

我从本地 WorkBuddy 记忆核对了以下经验，docs/15 吸收得基本正确：支付宝账户/余额是两种视角且重叠（451 对共享标识、16 对方向为“其它”）；微信同单号 141/12 组、296/24 行全部保留；15 条主金额与接收金额不一致；建行 1,863 条且两份字节相同只计一次；镜像与凭证不并入；不整表求和、镜像两侧不相加、红包保留两种金额视角、归一化前不汇总。

产品当前的做法与这些原则一致：不合并、不去重、不算净额、关系只作候选、未知不填零。建议下一步补三块：

1. **支付宝账户↔余额候选**：私有研究已有 451 对共享标识的直接证据，但当前产品关系查询只做微信↔建行；这是最便宜、最有价值的下一条勾稽能力（只读、带方向冲突警告）。
2. **材料覆盖面板**：像“账户覆盖并不完整”这种事实，产品目前只能看到文件列表；建议显示“已导入账户 / 时间段 / 缺口”，让“全量”这个词有边界。
3. **原值差异筛选**：WorkBuddy 的 34 列表把“原始值 vs 归一值”并排，可筛出所有加工行；产品现在只有详情，建议加“原文≠标准”筛选，并区分规则换算（单位/符号/舍入/映射）和人工修改（后者需要独立审计记录）。

> 🧠 **From Hindsight memory (FundSift 总览)** — 产品核心差异点是跨人跨渠道“并表”，Phase 1 验收还包括导出与手工并表复现；当前预览覆盖导入/查询/回源，导出与并表基准仍属下一阶段。

## 7. 建议的下一步顺序

1. 修 P1 重试 + staging 清理（不改业务规则，先让失败路径可用）；
2. 补 UI 三处（sticky 操作列、舍入可见、格式中文名）；
3. 再进“人工边界裁决”与完整 G0 冻结；
4. 之后做支付宝账户↔余额候选、覆盖面板、原值差异筛选；
5. 最后才是正式汇总/导出与并表基准。
