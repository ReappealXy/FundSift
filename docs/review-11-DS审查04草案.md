**草案可以通过。** 页面闭合度高、状态分离口径清晰、Q01~Q11 建议全部合理、AC-01~34 是「反例型」用例（验证的是『拒绝/不混/不冒充/不静默』，不是『按钮能点』），能发现真实错误。

以下意见按严重程度排列。

## 二、审查意见

### 意见 1（中）· P00 视觉方向需要一个明确的「已确认」来源

- 章节：5.1 / 依据文件表（ui-01-介绍首页.md）
- 反例：docs/04 写「采用已经确认的白色科技风格」；但对话历史里，你确认过的是**工作台**样式（浅灰/深蓝/紧凑），首页第一版被否、第二版（深蓝 hero + 横向案件卡）交付后尚无「确认」记录。若「白色科技风格」来自 ui-01 的新稿，属另行设计，请明确它是你拍板的新方向。
- 后果：P00 与工作台视觉衔接要么风格割裂，要么按「未经确认的风格」开工。
- 修订建议：在 ui-01 与 docs/04 里标注视觉决定的出处与确认时间；P00（展示型）与工作台（紧凑型）的差异可以存在，但要写明边界。
- 是否需用户拍板：**是**（看 ui-01 效果后确认）。

### 意见 2（中）· 多原因待核缺独立存储条目

- 章节：3.3 / 12.1（M05）
- 反例：3.3 要求界面分清「金额待核 / 缺时间 / 缺账户」等逐项原因，且「金额已确认、尚缺时间」的记录仍是 pending；但 fund_flow 只有 status 单字段，M05 只在文字里提到「缺逐项原因」，没有独立编号与建议结构。
- 后果：实现时若无 pending_reason 表，就只能把原因塞进 JSON 或重复写 status，AC-16/AC-19 无法验收。
- 修订建议：M05 明确补一张 pending_reason（record_id, reason_code, detail, created_at, resolved_at）或多原因清单结构，与「记录确认状态」解耦。
- 是否需用户拍板：否（数据建模建议，实现期定）。

### 意见 3（轻）· 验收矩阵缺「冻结保护」与「搜索范围」两用例

- 章节：13 / M1 / Q09
- 反例：AC-14 覆盖 A~F 但没覆盖「verified≥1 的规则被 UPDATE 必须拒绝」；Q09（流水搜索是否跨案）没有任何对应 AC。
- 后果：M1 的冻结探针只存在于 docs/03 里程碑，13 节矩阵少一环；Q09 决定后无验收载体。
- 修订建议：补 AC-35（冻结规则原地 UPDATE / 解冻 / 错误 unit 配对均拒绝，变更新增版本）；补 AC-36（首版搜索范围：跨案只搜案件、流水只搜当前案，界面明示范围）。
- 是否需用户拍板：否。

### 意见 4（轻）· balance_check「每笔唯一」与「人工接受历史」的冲突需在 DDL 修订时一并解决

- 章节：9.3 / M05 / docs/03 DDL
- 反例：docs/03 的 balance_check 是 UNIQUE(fund_flow_id)（重跑=UPDATE）；9.3 要求「单纯 UPDATE 会丢失旧依据或错误保留 manual，必须补历史与输入版本机制」。两者冲突已由 9.3 自认，但 12.1 未把它列为独立 M 项。
- 后果：实现时要么违反 9.3，要么临时发明表结构。
- 修订建议：M05 明确补充「balance_check 当前行 + 检查历史行（含输入版本、人工接受依据）的分层结构」，修订 DDL 时同步。
- 是否需用户拍板：否。
