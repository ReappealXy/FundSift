# 下一阶段实施规划：导入收尾与单笔人工复核（待确认）

日期：2026-11-19。第 0 节记录用户随后批准的实施范围，其余章节保留原规划及人工复核草案。

## 0. 已批准的实施顺序和底稿合同

先交付导入收尾和只读 Excel 底稿，再根据底稿讨论微信、支付宝业务口径，随后规划单笔复核与正式并表导出。人工复核、规则变更、成功材料主动重导、正式导出与 G0 冻结由后续阶段确认。完整 G0 是正式验收条件，独立样本审核可并行推进。

| 导出列组 | 内容 |
|---|---|
| 身份 | 案件、材料名、平台、原件文件名和 SHA256、批次号、格式及规则版本 |
| 来源 | 工作表、Excel 行号或 CSV/TXT 逻辑记录号、原始坐标 |
| 原文 | 金额、方向、余额、币种、交易时间，本方与对方账号/卡号，微信主金额与接收金额 |
| 标准值 | 金额（元，两位小数，未知留空）、方向、时间、币种和币种依据 |
| 状态 | 业务状态原值与规则归一值、证据状态、全部未解除原因码及对应说明 |
| 派生项 | 是否计入规则口径收付（是 / 否 / 未知，仅供参考）、金额换算、舍入、符号说明 |
| 说明页 | 案件与数据版本、时间、原因码含义、总行数及分平台计数、材料缺口、Excel 内编辑与复核的区别 |

使用 ExcelJS 写出 XLSX。有效流水沿用 `EFFECTIVE_FLOW_FROM`，逐笔字段、原因和统计从同一 SQLite 读事务取得。开始和发布前校验数据版本。Excel 未知金额保留为空单元格，账号和卡号写入文本单元格。金额超过 Excel 可保留分位的数值范围时，用两位小数文本保留精度。说明页标注底稿是规则结果、在 Excel 修改不会形成软件复核记录。文件名带数据版本和时间戳，先写同目录临时文件，再原子发布完整文件并防止覆盖。输出收付计数和流水覆盖信息，不输出金额合计。现有微信两列规则与收付方向保持原口径。

失败重试仅适用于没有当前有效批次的材料。已有有效结果的规则重导作为独立动作，完成后才允许切换当前批次。开始支持对已复核材料重导时，须提示未继承人工结论涉及的流水数，并能查看旧批次历史。归档查询以 `import_batch.archive_entry_id` 等正向引用为准，补回归防止业务读取冗余列 `archive_entry.batch_id`。

后续复核模型采用动作类型与逐原因处置。原待核原因的详情和解除历史保留，说明存入追加的人工记录，重新待核增加新原因。首轮复核只开放届时获得批准的动作，验收逐原因处理、剩余原因可见、历史可查以及整笔写入的原子性。

### 为什么推荐先人工复核

现在已能把材料导进来、找到异常并回到原文，缺少的是“人核实之后，软件怎样保存结论、依据和修改历史”。先确定这套数据含义，后续导出才有稳定的当前值、待核原因与人工历史可以输出。

导出在技术上也可以先做成只读导出，并不要求全部待核先解决。本规划选择先复核，是产品推进建议，由用户决定方向。

支付宝余额明细与账户明细勾稽、材料覆盖面板仍有价值；前者还需新的格式与视角规则批准，后者属于后续材料完整性能力，建议分别立项。

## 2. 前置交付：现有预览收尾

### 2.1 失败材料显式重试

现状：底层导入具备 `reimport` 能力，但桌面接口未开放。已登记同哈希材料被统一判重，首次导入失败后用户没有重试入口。

建议行为：

- 材料“没有有效当前批次，且没有进行中的任务”时，显示“重试导入”。
- 复用材料身份和归档副本，追加新批次，保留原失败批次及错误。
- 重试前重新核验归档身份和适用规则。归档不可用时明确报错；若提供重新选择原件，必须核验同一哈希。
- 已有有效结果的材料继续阻止普通重复导入；成功材料的主动重导另行设计。
- 结构确实损坏的文件可能再次失败。重试提供恢复机会，不承诺把不支持的文件修好。
- 即使最近一次批次失败，只要原来仍有有效当前批次，也不因“最近失败”静默替换成功结果。

涉及位置：`import-service.cjs`、`desktop-data.cjs`、`main.cjs`、`preload.cjs`、`worker.cjs`、材料页。

### 2.2 接入超期暂存清理

现状：`cleanupStaging()` 有实现和测试，生产打开案件流程仅检查恢复清单，没有调用清理。

建议在案件打开后的恢复流程中，依照现有 24 小时宽限、事务内实际引用检查及无活动导入的条件，清理可确认无用的 staging。只处理暂存，最终归档和历史批次不受影响。损坏的恢复清单不自动删除；清理失败需反馈，不能伪报已清理。

单 worker 的串行队列作为任务互斥依据；不能只看新建 ArchiveStore 实例的局部 active 集合为空，就认为系统没有任务。清理结果显示数量；无法判断的条目保留并说明原因。

### 2.3 补齐直接影响使用的展示

- 1024×720 下原文操作保持可达，待核原因可完整查看。
- 原文详情直接展示单位换算、符号处理、舍入前后值；技术证据仍可展开查看。
- 材料格式显示中文名，格式键放详情。
- 附加诊断单列数量及说明，不混入待核数。

规则批准证据与私有决定文件的身份关联在正式 G0 冻结前补齐；已冻结规则不得原地改写。`archive_entry.batch_id` 的语义另行梳理，不简单给可由多批次共用的归档回填一个批次号。

本步验收：首次失败后可重试、再次失败可解释、成功材料仍判重；超期无引用暂存可清理，活动/有引用/未到期/清单损坏均保留；原件哈希不变；小窗口原文及原因可访问；源码及最终 EXE 链路通过。

建议提交文案：

```text
Summary: 修复失败导入重试并接入暂存恢复清理
Description: 增加无有效批次材料的显式重试，保留失败历史；接入受引用和宽限保护的暂存清理，补齐原文操作、换算说明、中文格式及附加诊断展示。
```

大白话：先解决“失败一次就卡死”和“失败留下的半截文件没人收拾”，再把关键信息放到看得见的位置。

## 3. 下一主功能：单笔人工复核与处理历史

### 3.1 首版建议范围

进入异常复核页 → 选一条记录 → 对照原文与规则结果 → 填写结论及依据 → 保存 → 查看当前结果和处理历史。

建议首版支持：

1. 对单笔待核记录确认标准金额和方向。
2. 证据不足时保留待核，追加核查说明，不要求编金额或填零。
3. 查看历史；对人工处理过的记录追加更正或重新复核，保留全部旧依据。该能力需用户明确批准。

是否本轮同时加入“交易关闭”和“主/接收金额差异”的专门处置，列入第 7 节待决定事项。首版不默认扩展到普通已确认记录的任意编辑、时间账户补录、批量处理或关系确认。

### 3.2 36 条待核不能共用一个确认按钮

| 当前类型 | 现象 | 复核设计要求 |
|---|---|---|
| 支付宝方向“其它” | 金额方向含义未确定 | 有独立证据才确认金额/方向；证据不足继续待核 |
| 支付宝交易关闭 | 即使金额可解析，也不代表交易已经发生 | 不能通过填写相同金额解除业务状态原因；需专门处置口径 |
| 微信主金额与接收金额不同 | 主金额已有值，两个视角有差异 | 分别保留原值；不自动用接收金额替换、不拆费用、不抵消 |
| 建行负额消费退货 | 负号与借贷组合含义需要核实 | 不自动反向；先核对来源及证据，再进行获准的人工解释 |
| 其他缺字段或多原因记录 | 金额解决后仍可能缺时间、账户或币种 | 只解除本次有依据解决的项，其他原因继续保留 |

不以待核数量清零作为验收目标。证据不足时，“核过，继续待核”也是有效结果。

### 3.3 页面行为

- 队列按记录计数，显示该记录全部未解决原因；多个原因不重复算多条流水。
- 详情展示原始字段、来源单位、初始规则解释、当前标准值、规则与来源版本、原文入口及历史。
- 金额输入绝对值，单位为元；方向由人主动选择，不默认猜成收入或支出。
- 金额采用严格十进制字符串，最多两位小数，精确转整数分并检查 int64 范围。零值是否可确认须有该类型批准依据。
- 保存前明确显示将改变的字段、将解除的原因和仍保留的原因。
- 保存成功后刷新记录、队列及案件计数；失败时保留输入，页面不提前移走记录。
- 界面分别标明“按规则得到的结果”和“人工复核结果”。当前 confirmed 不等于已经人工逐条审签。

### 3.4 数据与事务

建议复用现有 `pending_reason` 和按流水范围的 `runCaseTransaction()`，增加正式复核历史模型和服务。具体表名/迁移版本在施工设计时确定，不提前修改数据库。

每次人工动作至少追加保存：

- 请求唯一标识、案件、材料、批次、流水及原始坐标。
- 输入案件数据版本、规则/解析身份，以及原始规则解释的关联。
- 动作类型、修改前后标准值、前后状态、逐项原因的处理结果。
- 依据、操作时间和本地操作人声明。

原始文本、归档、来源坐标及冻结规则继续不可改。首次人工操作前固定初始标准解释；后续当前值可以变化，历史不能覆盖、删除或通过 REPLACE 绕过。

一次保存须在同一事务内完成：验证当前案件/有效批次/输入版本 → 校验动作权限与业务规则 → 写历史 → 更新获准标准字段 → 解除明确获准的原因 → 根据剩余原因计算状态 → 更新数据版本及计数。任一步失败全部回滚。

请求重复提交返回同次结果，不生成重复历史；相同请求标识带不同内容则拒绝。表单打开后若数据变化，旧提交明确要求刷新。重新导入的新批次不自动继承旧批次人工结论，旧历史仍可追查。

“保留待核并记说明”只新增历史，不改变金额或解除原因。“重新复核”通过追加事件和必要的新待核项表达，不改写已经解决的旧原因。

涉及位置：新增复核服务和迁移；扩展 `desktop-data.cjs`、worker/main/preload 白名单；接入异常页和流水详情。具体动作需由服务端按原因类型判断，不能让界面传任意字段直接写库。

### 3.5 为什么余额接受暂不一起做

当前三个具体格式的余额仍按未知口径保留，没有已验收的完整余额链。余额接受必须先有可比链段、前项及输入版本，不能凭一个按钮制造“余额通过”。这项建议后续独立设计。

## 4. 独立基准审核与产品复核分别推进

完整 G0 是“独立标准答案能否作为验收依据”；产品复核是“日常用户怎样有依据地修改或保留待核”。两者分别保存，不能用产品当前值反过来生成唯一预期答案。

建议用户批准后，可先用合成数据建设人工复核底座，并行整理真实样本的人工审核清单。涉及真实类型的产品验收，使用独立、人工批准并固定身份的子集预期。

完整 G0 仍需完成 A 层按来源抽查、B 层边界裁决、五种样本角色、41 项覆盖和正式冻结。三格式预览与子集验收不替代完整 G0，不自行宣布正式 M1 或第一片完成。

B 层批准可以批准“这条保持 pending 是正确答案”，不要求把现有 36 条都改成 confirmed。若规则仍规定负值待核，不能只加一条批准记录就更改解析预期；规则变化需新增版本并重新审核。

大白话：一条线是在核准“测试答案”，另一条线是在做“软件里的人工处理”。两份东西不能互相替代。

## 6. 后续接正式并表导出

复核完成后，建议再确认并实现正式导出。保留每个来源记录，输出当前标准解释、待核原因、来源与人工历史，绑定同一数据版本。未知金额留空，账号按文本保存，材料未入表的缺口要说明。

导出可包含待核，不要求全案没有问题；原始记录合表也不等于已确认跨平台重复、可以删除镜像或能计算经济净额。导出范围、XLSX/CSV、保存位置、拆分和历史要求届时单独确定，不从演示行为自动带入。
