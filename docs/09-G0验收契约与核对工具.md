# G0 验收契约与核对工具：供 DeepSeek 审核

日期：2026-11-18。本轮根据用户提供的规划，先交付 G0 的数据契约、覆盖矩阵模板、核对工具和合成反例。**本轮没有读取真实流水，没有生成真实逐行答案，也没有完成 G0 或开始 M1。**

## 1. 对规划的采纳与边界

采纳 A 层机械生成、B 层人工裁决的分工。普通行不要求几千次重复签字；先批准每个格式的规则卡，再独立生成 A 层，人工按源文件抽查。异常和边界行进入 B 层，记录依据并由人批准。

需要收紧三点：

1. **B 层不能只由生成器报告“不确定”。** 冲突决策表、缺字段、零金额、冲回、余额不可比、舍入和其他覆盖矩阵边界必须强制筛查。即便程序很自信，也不能把这些行自动当作普通 A 层跳过人工裁决。筛查规则和漏筛反例要接受独立审查。
2. **核对工具不证明业务答案正确。** 工具可以检查字段、引用、整数、状态约束、数量与哈希，却不能替代“这份材料的负号到底是什么意思”的规则证据和人工裁决。把一套错误答案写得自洽，仍可能通过结构检查。
3. **文件身份、行数和坐标真实性分别验收。** 哈希匹配说明字节没有换；答案数量与清单一致说明没有数量差；二者都不能单独证明坐标指向的是真实交易，也不能证明抽取过程中没有漏一笔、补一笔。后续仍需独立提取原始记录清单、核对表头与非数据行，不能让被测解析器自己提供唯一的坐标依据。

## 2. 五个产物如何落地

| 产物 | 本轮形式 | 填充与审核责任 |
|---|---|---|
| 样本清单 | 私有 `bundle.json` 的 `sources[]`；结构由 `schemas/g0/bundle.schema.json` 约束 | 记录文件名、字节数、SHA256、非敏感案件代号 `case_ref`、样本角色 `sample_role`、渠道、格式、账户引用、时间范围、编码/BOM/合并单元格观察、数据及非数据记录数；清单批准人须确认计数口径与依据 |
| 每格式规则卡 | 同一 bundle 的 `rules[]` | 固定 `format_key + rule_version`、A～F 类、元/分与倍率、方向词表、负号/零值策略、余额口径、币种声明及证据；不是按“微信/支付宝”平台名统一猜规则 |
| 逐行答案 | 私有 `answers.jsonl`，每行一个完整 JSON 对象；schema 的 `$defs.answer` 规定字段 | A 层由独立生成器产生并抽查；B 层逐条记录依据、问题关联和批准信息 |
| 待确认问题 | bundle 的 `questions[]`，答案行以 `question_ids[]` 引用 | 每项包含问题、受影响文件/行、候选项、建议、最终决定、决定人和时间；未知保留为 open，不能自动当作已批准 |
| 核对工具与覆盖矩阵 | `scripts/g0/validate.cjs`、`schemas/g0/coverage-matrix.json` 及合成测试 | 检查结构、关联、不变量、哈希和固定覆盖要求；工具实现与将来的被测解析/金额引擎分离 |

模板位于 `docs/g0/templates/`。复制后在 Git 忽略的私有目录内填充，不直接把真实内容写回模板。空模板是结构草稿，不能当作验收样本。

当前结构版本为 v3，覆盖矩阵 v4 共 **41 项：40 项行级、1 项文件级**，覆盖 A～F、冲突表各分支、单位与舍入、四种余额口径、金额/余额状态隔离、同秒顺序、链段完整性及币种边界。`unknown_format_file` 是文件级待识别用例，不允许通过虚构一条 `fund_flow` 来凑覆盖。

v2 新增 `time_timezone_marker` 和 `amount_unparseable`：带时区／UTC 标记的原始时间保持本地标准时间未知、整行 pending；非空但无法按本版十进制语法解析的金额保持 amount=null、pending。两者均保留原文并具有对应独立原因，不能静默转换时间、规范化全角数字或用零顶替未知。这些约束在未贴覆盖标签时同样检查。

矩阵 v3 增加 `time_ambiguous` 和 `currency_mapped_cny`。区间或与负偏移含义不明的时间保持原文、`txn_time=null`、pending，必须具有独立 `time_ambiguous` 原因，不擅自取端点、不算时区覆盖；非 ISO 币种可用绑定格式规则卡中已批准的 `currency_map` 确认。该次交付和历史验证见 [时间歧义与币种映射](11-G0时间歧义与币种映射.md)。

矩阵 v4 增加 `time_zone_abbreviation`，缩写大小写不敏感并匹配完整词。多义名单为 CST/IST/EST/PST/BST/AST/GST/MST，明确标记名单为 UTC/GMT/JST/KST/HKT/SGT/AEST/AEDT/CET/CEST/MSK；这是本契约的固定处理口径，不断言缩写在全球单义。区间（含尾注）优先判为含义不明，时间后夹有文字才出现标记也须含义待核；明确时区后的括号／备注不能令标记漏网。缩写覆盖须实际命中名单，且原因与最终分类一致：ambiguous 必须有精确的 `time_ambiguous`，timezone 必须有包含 time/timezone 且不是 `time_ambiguous` 的原因。具体边界、反例及版本迁移见 [最新交付](12-G0时间尾注与缩写识别修复.md)。

覆盖项标签只是定位与计数入口。每项的 `description` 规定原始条件和期望要点，审查时应逐项核对，不能把“贴满 41 个标签”等同于业务覆盖真实成立。

为防止“行数相同但漏一行、补一行”，正式清单还要求每个文件提供独立的 `record_index`：JSONL 每条仅含 `source_loc` 与 `kind`，`kind` 为 `data/header/footer/other`。索引分类数必须与清单观察一致，答案坐标集合必须完整等于其中 `data` 集合；不能以表头充当交易行，不能随意把第 1 行改成第 999 行。CSV/TXT 坐标还受逻辑记录总数约束。索引自身的 SHA256、提取方法名称／版本、代码路径和代码 SHA256 都会核对；正式模式要求 `independent_of_parser=true`。索引、提取方法及其输出继续保存在私有目录。

索引示例（仅格式示意）：

```jsonl
{"source_loc":"1","kind":"header"}
{"source_loc":"2","kind":"data"}
{"source_loc":"3","kind":"footer"}
```

索引提取与金额生成是两项责任：前者只定位原始记录与非数据记录，后者独立形成标准答案。工具不执行提取代码，也不能靠哈希证明它确实正确读过原件；提取方法和数据／表头分类仍需人审。当前只实现核对与合成夹具，真实三格式的独立坐标提取器尚未编写。

## 3. 答案如何对齐数据库

答案的外层保留 `source_id`、`source_sha256`、`source_loc`、`format_rule_id`、`rule_version`、`layer`、`basis`、`review`、`coverage` 和 `question_ids`。

`raw` 保留原始金额、方向、余额、收入/支出双列、时间、账户、币种和摘要文本。标准结果放在 `expected`：

| 答案字段 | 对应关系与约束 |
|---|---|
| `amount`、`direction`、`status`、`balance`、`currency`、`txn_time`、`acct_no`、`reversal_flag` | 对齐 `fund_flow` 的标准值；金额与余额均为整数分，进为正、出为负 |
| `pending_reason[]` | 对应关联表的未解除阻断项，逐项保留 `reason_code` 与 `detail`；不是把所有问题合成一个布尔标记 |
| `balance_scope`、`balance_check` | 是关联余额结果的验收投影，不宣称它们全是 `fund_flow` 的列；当前数据库的结果与历史继续分层 |
| `balance_check.previous` | 用来源文件与坐标引用前项；不预造本机数据库自增 ID |
| `source_loc` | XLSX 使用约定的 sheet 名与原始表内行号；CSV/TXT 使用逻辑记录号，引号内换行不增加逻辑记录数 |

“未知”使用 JSON `null`。金额未知必须 pending 且有原因，不能用 0 顶替；真实的零金额保留 0，再按规则卡决定是否待核。因缺时间或账户待核，但金额已可靠时，应保留已知金额，整行继续 pending。`confirmed` 不能带未解除阻断原因，`pending` 必须具有原因。

余额异常与金额状态独立：可靠金额可以 confirmed，同时余额检查 fail；不能为了凑平余额自动改向。只有 asset_ledger、规则明确同向、同账户同币种、前项可用、段落完整且顺序稳定时，才允许按前余额加本笔金额核对。debt、available、unknown 及不完整/无前项/顺序未定的情况须说明不可比原因。

核对工具拒绝余额前项成环、跨案件、未知账户或币种、混用余额口径、时间倒序及 pending 记录参与判平，差额口径固定为“实际余额 − 期望余额”。已知原始 ISO 币种不得换成 CNY；B/C/E 类方向缺失或不在词表内时须待核。同案同 SHA256 原件不能换 `source_id` 重复登记。比较三字母 ISO 币种时仅忽略首尾空格和大小写，原文不改写。非空标准币种必须有原始 ISO 或对应格式已批准的映射证据；原文缺失时，仅已批准的 `verified_cny` 规则可声明 CNY，不能默认 USD 等外币。

每条规则必填 `currency_map`，没有映射填 `{}`。例如 `{"人民币":"CNY","156":"CNY"}`，键须为首尾无空白的非 ISO 原文，值为大写三字母标准代码；比较时仅对原始文本 trim，再精确匹配。映射随本规则版本的 `review` 一起批准，不跨规则复用、不提供缺币种默认值，也不能写三字母键去覆盖 ISO 证据。映射已批准且命中时标准币种必须保留该结果；未命中或未批准时非 ISO 币种保持 null、pending。规则批准只是证据声明，真实格式是否确实使用该映射仍须人审。

普通已批准映射行只承担 `amount_a` 等普通金额覆盖、且无其他异常时，可以属于 A 层；不能把全部映射行强制逐笔人工裁决。承担 `currency_mapped_cny` 边界见证的行须进入 B 层，是覆盖标签的边界要求，不是映射本身自动把整列降为 B 层。真实规则卡仍应把币种映射及批准依据单列一节。

`reason_code` 使用稳定的机器代码并与中文 `detail` 分开。本版最低关联检查要求：未知时间代码包含 `time`；未知账户包含 `account` 或 `acct`；未知金额包含 `amount/direction/format/sign/column` 之一；词表外方向包含 `direction/sign/format` 之一。合成夹具分别使用 `time_missing`、`account_missing`、`amount_missing`、`direction_unknown` 等。最终解析／复核服务词表尚未实施，接入时须明确映射，不能让中文说明代替原因代码。

金额、余额及差额支持两种无损表示：JavaScript 安全整数范围内可用 JSON 整数；超出该范围时使用十进制整数字符串，由 `BigInt` 核对并无损映射数据库 INTEGER。两者均须处于 SQLite 有符号 int64 范围 `[-9223372036854775808, 9223372036854775807]`。不能把 int64 边界金额写成已经失真的 JSON number；工具拒绝小数、指数记法的金额和越界值，不自动舍入“修复”答案。计数和版本仍受各自 schema 的非负/正安全整数约束。

该约束只作用于标准答案的整数分；原始十进制文本照原样保留。原始“元”金额需要舍入到分时，其规则和舍入依据仍按 `docs/02 §4.3` 独立产生，不能把核对脚本变成被测金额引擎的另一入口。

## 4. 草稿通过与正式验收必须分开

草稿模式允许尚无样本、尚未批准的规则、未关闭问题和未完成覆盖，但不允许已填入的内容违反结构或基础不变量。报告必须区分 `ok` 与 `ready_for_m1`：草稿 `ok=true` 只表示当前草稿符合约束，不能宣传 G0 完成。

正式模式 `--release` 要求至少包括：

- 数据集标记 frozen，schema、覆盖矩阵、答案文件及独立生成器文件的实际 SHA256 与记录一致。
- 具有已批准的真实样本角色：`ccb_xlsx`、`wechat_txt`、`alipay_account_csv`、`alipay_balance_csv`、`case_b_reversal`。这些角色与案件代号、格式及来源相符；41 项合成覆盖不能替代真实样本准入。
- 文件清单逐个核对原件大小及 SHA256；答案行数与该文件清单的 `data_records` 一致，`(source_id, source_loc)` 唯一，所有引用存在且绑定规则版本一致。
- 每个文件带有独立原始记录索引，索引分类计数及答案的完整数据坐标集合相符；索引内容与独立提取代码的哈希均已固定。
- 清单与规则卡有人批准并记录批准人、时间和依据。清单批准包含人工确认行数与非数据行分类，而不是只有一个 approved 字样。
- B 层全部批准；每个有 A 层行的源文件至少有一条人工抽查批准记录。至少一条是最低门槛，不是声称一条抽查已具备统计保证；实际抽查比例仍要按格式与风险确定。
- 所有影响当前版本的问题均 resolved，具有决定、决定人和时间；允许最终答案为“仍未知，因此 pending”，不允许为了关问题伪造金额。
- 固定覆盖矩阵满足最低要求，并接受原始条件与判定依据的独立检查。
- 使用外部保存的预期 bundle SHA256 固定验收对象，不能只信 bundle 文件对自身的声明。

批准记录及生成器 independence 说明都是可审计的声明，不是身份认证或“独立性已经被密码学证明”。DeepSeek 与用户仍需检查谁批准了什么、生成器是否复用了被测代码、抽查是否覆盖风险。正式报告中的 `ready_for_m1` 仅表示契约门槛通过、可作为 M1 输入候选，不证明全部业务答案正确，也不代替 Q05/Q11 等业务范围确认。

## 5. 运行与版本固定

在仓库根目录运行：

```powershell
npm run test:g0
npm test
node scripts/g0/validate.cjs docs/g0/templates/bundle.json --json
node scripts/g0/validate.cjs golden-samples/g0/v1/bundle.json --source-root golden-samples/g0/v1 --json
```

最后一条以填充后的私有目录为例。`answers_file` 和生成器 `implementation_path` 相对 bundle 所在目录解析；原件 `sources[].path` 相对 `--source-root` 解析，未指定时使用 bundle 所在目录。路径必须留在对应允许根内，不能靠 `..` 或符号链接越界读其他文件。工具不修改原件、答案或 bundle。

`record_index.path` 及其提取代码 `implementation_path` 同样相对 bundle 目录。路径使用 `/` 分隔，不用盘符或绝对路径。开发依赖固定为 AJV 8.20.0，用于 JSON Schema 2020-12 校验；运行工具使用本轮的 Node.js 22.20.0，数字词法检查依赖 JSON reviver 的原始文本上下文。桌面版仍为 0.1.4，本轮没有更改产品代码或重新打包 EXE。

确认全部内容、取得 bundle 哈希并将其保存到独立审查记录后，再运行正式检查：

```powershell
node scripts/g0/validate.cjs golden-samples/g0/v1/bundle.json --source-root golden-samples/g0/v1 --release --expected-bundle-sha256 <独立保存的64位SHA256> --json
```

上面的占位符需替换为真实哈希，不是原样执行。正式验收应明确固定的数据集版本、规则版本、生成器版本、schema/matrix 哈希和 bundle 哈希。当前结构版本 `schema_version=3`、覆盖版本 `matrix_version=4`，由 `schemas/g0/bundle.schema.json` 中两项 `const` 固定；旧结构 v1/v2 或矩阵 v1/v2/v3 均报 SCHEMA，不得为了兼容放宽常量。本轮采用 A 方案：矩阵常量变化会改变 schema 内容，因此 schema 也另升新版本并更新 `$id`，不让同一个版本号对应两份不同契约。升级需另存新数据集版本、补齐新见证、复核受影响规则与答案批准并重新固定哈希，不能仅改版本号沿用旧审批结果。

改规则、新增裁决或修正答案时，创建新 `dataset_version` 和新目录，规则变化另增 `rule_version`；保留旧文件及旧哈希，不原地改写已冻结版本。校验器能够发现与外部固定哈希不一致的修改，但单靠某次本地运行不能证明目录在历史上从未被替换，版本保存仍是交付流程的责任。

## 6. 私有数据与 Git 边界

原件、填充后的清单、规则证据、逐行答案、详细问题与裁决、生成器对真实材料的本地输出，放在 `golden-samples/` 等已被 Git 忽略的私有目录。延续既定决定：内部样本不脱敏，仅内部使用，不外发。

Git 只提交空模板、schema、覆盖矩阵、核对工具、纯合成夹具和不含真实交易内容的交接记录。若需要在 Git 保存样本哈希或问题摘要，只使用不含真实文件名、账户、交易描述和原文摘录的稳定代号；有敏感明细的问题本体继续放私有 bundle。`.gitignore` 不会阻止手动强制提交，提交前仍需检查暂存差异。

本轮没有为真实文件计算哈希，没有复核历史笔数，也没有重新要求用户提供原件。微信 5635、支付宝 607/397 等历史数字仍是待原件复核的线索，不能填成已确认清单数据。

## 7. 本轮验证口径与尚未完成事项

工具使用纯合成文件和答案检查合法输入、字段缺失、重复坐标、错误哈希、非法整数、符号冲突、pending 原因、问题决定、余额状态、未知格式文件和路径范围等反例。首版（矩阵 v1）G0 专项 **46 项通过**，其中完整冻结正例走通 36 项覆盖、五种样本角色、独立索引、人工记录与外部哈希门槛；反例验证篡改与缺项被拒绝。规则声明负值待核时，不能仅加 B 层批准就绕过规则卡确认。该夹具中的 `real`、approved 和角色仅模拟准入分支，不是真实样本或实际人工审批。测试在临时目录生成并清理，不给真实 G0 颁发合格结论。

## 8. 请 DeepSeek 重点审核

1. schema 是否准确区分原始值、标准值、关联待核原因和关联余额结果，是否允许未知但拒绝把未知冒充零。
2. 数字校验是否在 JSON 读取时保留足够证据，能拒绝小数和精度损失，而不只是依赖 `Number.isInteger` 检查解析后的值。
3. 引用、路径、原件哈希、答案数量与源身份是否被真正核对；是否存在改一份文件后只更新它自身哈希即可冒充正式验收的漏洞。
   独立记录索引是否确实覆盖所有逻辑记录，答案是否与其数据坐标逐条一致；索引提取器和被测解析器是否真正独立，是否把“声明独立”夸成证明。
4. B 层强制筛选、A 层逐源抽查、规则和清单批准是否明确；是否错误地把 review 字段填写完整当作业务正确证明。
5. 41 项覆盖是否完整且有真实条件约束；区间、尾注、非紧邻标记与多义缩写是否保持正确原因，缩写覆盖是否具有实际名单见证；币种映射是否限定批准的规则版本，普通映射行是否仍可按已批准规则属于 A 层；未知格式是否保持文件级；外币、零值与待核边界是否擅自补了未确认策略。
6. 草稿成功、工具合成测试成功和 G0 正式通过是否严格区分；是否保留了独立坐标清单、生成器独立性与人工判定的局限。
7. 版本与外部哈希固定是否足以明确本次审查对象，文档是否夸大了本地检查对历史不可变性的保证。
8. Git 中是否只出现模板和合成材料，错误报告、夹具及提交说明是否泄露真实数据。

## 9. Git 提交文案

### 第一步：定义验收契约与覆盖矩阵

Summary：`定义G0答案契约与固定覆盖矩阵`

Description：

```text
定义样本清单、格式规则卡、逐行答案和裁决问题的版本化结构。
保留未知金额、独立待核原因与余额结果，明确A层抽查和B层人工批准。
提供41项固定覆盖要求及空模板，真实原件与填充答案继续排除在Git之外。
```

大白话：先规定标准答案应该写什么、哪些特殊情况必须有例子，不往表里猜真实数据。

Summary：`增加G0独立核对工具与反例检查`

Description：

```text

```

大白话：配一把会拦错的尺子，但不把“尺子检查过了”说成“业务答案一定对”。
