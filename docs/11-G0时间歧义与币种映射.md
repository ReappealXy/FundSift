## 1. 本轮处理结果

| 问题 | 当前行为 |

DeepSeek 建议的“完整时间戳锚定”示例本身仍会匹配 `2026-11-18 08:00-09:00`，且漏掉原来支持的 `+08`。本轮没有直接照抄，而是把明确时区与区间／偏移歧义分开判定。两种情况都会待核，但原因和覆盖见证不同。

## 2. 时间的具体识别范围

| 原始文本示例 | 分类 | 标准答案要求 |
|---|---|---|
| `2026-11-18 08:00-09:00`、`08:00-09:00` | 时间含义待确认 | `txn_time=null`、pending、`time_ambiguous` |
| `2026-11-18 08:00:00-09:00:00` | 时间区间 | 同上，不自动取区间端点 |
| `2026-11-18 08:00:00 - 2026-11-18 09:00:00` | 时间区间 | 同上 |
| `2026-11-18T08:00:00-09:00` | ISO T 分隔的明确负偏移 | `txn_time=null`、pending、有时间／时区原因 |
| `2026-11-18 08:00:00-0500`、`2026-11-18 08:00:00-05` | 紧凑负偏移 | 同上 |
| `2026-11-18T08:00:00+08`、`+0800`、`+08:00` | 明确正偏移 | 同上 |
| `2026-11-18T08:00:00Z` 或带 UTC/GMT 标记 | 明确时区 | 同上 |
| `2026-11-18 08:00:00` | 普通本地时间 | 沿用本地标准时间校验，不强制变成时区或区间待核 |

空格分隔时间后接 `-HH:mm` 可能是区间，也可能是负偏移；没有额外格式证据时不替人决定。T 分隔是本契约识别明确 ISO 偏移的约定，不代表工具证明了真实文件的语义。区间分隔支持连字符、短／长横线、`~`、`～`、`至`、`到`；这不是通用自然语言时间解析器。

`time_ambiguous` 不得用于凑 `time_timezone_marker` 覆盖，反之亦然。删除覆盖标签也不能把区间取起点后标 confirmed。对含义不明的时间只写 `timezone_marker` 或 `time_missing` 不够，须保留独立的 `time_ambiguous` 原因。

## 3. 币种映射契约

每条 `rules[]` 必须有 `currency_map`；没有映射时填 `{}`。下面是规则片段，不是已经批准的真实规则卡：

```json
{
  "currency_policy": "explicit",
  "currency_map": {
    "人民币": "CNY",
    "156": "CNY"
  }
}
```

规则卡的 `review` 批准覆盖整个规则版本，包括映射；仍需写批准人、有效时间与依据。映射不设全局默认，也不跨规则借用。具体要求如下：

- 原始币种只在比较时 trim，别名精确匹配；`" 人民币 "` 可匹配 `"人民币"`，原文不改写，不进行模糊匹配或字符替换。
- 映射键为非空且无首尾空白的非 ISO 原文，不允许空键、空白键或任意三字母代码键；映射值为大写三字母代码。沿用既有三字母代码判定，本轮未新增完整 ISO 币种字典。
- 映射只有在当前绑定规则版本 `review.status=approved` 且批准信息完整时才能作为有效证据。草稿可以保存未批准映射，但不能靠它确认币种。
- 已批准且命中的映射结果必须保留，不能改成其他币种或把已有证据丢成 null。未映射、未批准的非 ISO 文本保持 null、pending。
- 缺失原文不能靠映射补币种；只有已批准的 `verified_cny` 规则可声明 CNY，不能凭空推断外币。
- 批准的外币别名可以保留实际标准代码，作为 `currency_foreign` 见证；首版外币不混入人民币合计的边界不变，实际文件／行发布策略仍待后续业务确认。

批准字段是可审计的声明，不是身份认证。工具不能证明“156”在某个真实文件中确实表示人民币；这仍由格式规则证据和人工批准负责。生成真实答案前，需先审各格式规则卡，尤其是建行币种列。
