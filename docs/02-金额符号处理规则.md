# 02 · 金额符号处理规则（并表核心）

> 本规则是并表模块的设计依据，来源于三处证据：HYJX 221 格式全量扫描（静态配置）、DMSeek 解析代码片段、两案真实流水的实证。
> 带 ⚠️ 的项未经原软件运行验证。
> 修订记录：2026-11-12 按 review-03 修订；同日晚按 review-05 复核修订（F01 单位倍率、F02 余额语义、F05 冲突判定、F09 脱敏方案）。

## 一、问题定义

不同来源的流水，金额符号约定不同：

- 有的写「金额 100 + 收支=支出」；有的直接写「-100」；
- 负号可能表示**普通支出**，也可能表示**冲回**（原支出的退款收进）；
- **同一平台的不同文件格式也可能不同**：支付宝「账户明细」金额全正（方向单列），「余额明细」支出为负。

因此：**规则维度必须落到「来源平台 + 格式版本 + 文件/账户批次」，不能按平台名一刀切。**

## 三、逆向资料中的既有处理

### 3.1 HYJX：16 个含绝对值配置的格式分三类（221 格式中 160 带 XML）

| 类 | 处理方式 | 格式数 | 代表格式 |
|---|---|---|---|
| A | 按原金额正负生成方向，金额另取绝对值 | 5 | 农行005、招行001/002/004、资金查控平台2-003 |
| B | 「进+负金额→出」「出+负金额→进」反转方向，金额另取绝对值 | 9 | 广发004、湖北002、汉口001、建行003/006/010、兴业002、邮储002、招行003 |
| C | 金额取绝对值，方向沿用原标志/文字转换 | 2 | 农行003、资金查控平台2-001 |

- B 类完整配置链（广发004）：出账→出/入账→进 → 拼接原金额 → 进-→出、出-→进 → 取首字符 → 金额列取绝对值（交易金额2）→ 映射用「调整后方向 + 绝对值金额」。即「出账、-100」→「进、100」。
- ⚠️ C 类是否成立取决于源文件方向列是否已表达实际资金方向；**必须与对应格式真实样本配对验证**。
- 其余 144 个带 XML 格式未发现这三类配置：可能金额本身全正、也可能存在原生执行器逻辑，**不能默认它们同一种处理**。
- **单位换算**：微信格式对金额列配置 RegParam name="IN_EXP" 值 "$/100"（原始单位是分）——这是**外部模板把「分」变换为「元」**的显示/中间格式行为，**不是本软件入库倍率**（本软件标准存储单位就是分，见 §4.3）。
- 公共方向词表（lendingFlagConfig.json）只统一「借/贷/C/D」文字，**不解决负号语义**。

### 3.2 DMSeek

- mapProductNoBankRow（fundParse.bundle.cjs:116880）：带符号金额拆成「绝对金额 + 方向」（out.jyje = Math.abs(signed)；signed>0→贷、否则→借）；
- 山东农信某格式（同文件 :115580/:115692）：定长「存取金额」两栏——第一栏负数→收入、第二栏负数→支出，signedReversal 时备注「冲正金额」，冲正标志位非 0 备注「冲正:cz」；
- 其余分支仅见「取绝对值 + 方向单独读取」，正确性未证实。

## 四、本软件的统一规则（设计规则）

### 4.1 金额表达方式全分类（A~F）

| 类 | 原始文件形态 | 方向判定来源 | 金额取值 |
|---|---|---|---|
| A | 金额本身带符号，无方向列 | 金额正负 | 绝对值 |
| B | 方向列 + 金额可能带负号表示冲回 | 方向列 ± 负号反转 | 绝对值 |
| C | 方向列 + 金额只表示大小 | 方向列 | 绝对值 |
| D | 收入、支出分列 | 所在列 | 列值 |
| E | 方向列 + 无符号金额（最常见） | 方向列 | 原值 |
| F | 其他/未确认 | — | 进待核，禁止猜测 |

**判定顺序（按金额类别分支，每行固定走一遍）**：

1. 按该文件绑定的格式规则识别金额表达方式（A~F）；
2. 按类别分支：
   - **A 类**（无方向列）：直接读金额符号定方向，**不执行词表映射**；
   - **D 类**（收支双列）：方向由金额所在列位决定，**不执行词表映射**；
   - **C/E/B 类**（依赖方向字段）：方向词按该格式自己的词表映射为标准方向（收入/收/贷/C/进→进；支出/付/借/D/出→出），词表未收录 → 待核；
3. 再按该类别的冲突规则处理（下表）；
4. 仍无法判定 → F：该行进待核。

**冲突决策表（遇冲突即进待核，禁止静默默认）**：

| 情形 | 判定条件 | 处理 |
|---|---|---|
| D 类两列同时有效 | 两列**均为非零数值**（空值或 0 不算「有值」；「收入100/支出0」是正常行） | 待核（可能退一进一，人工确认拆单或标注） |
| D 类两列皆空/皆零、但该笔交易存在 | 无法确定金额方向 | 待核 |
| D 类某列为负 | 收入/支出列出现负数 | 按该格式已验证规则处理（如 B 类反转）；规则未定义 → 待核 |
| 方向字段与金额符号冲突 | 按该格式规则**声明的符号语义**比对：格式已定义则按声明处理（A 类负号即出；B 类方向+负号按反转规则；D 类负值按已验证规则），格式未定义或信息缺失才待核 | 按声明处理，否则待核 |
| 零金额 | 金额=0 | 按格式规则处理；规则未定义 → 待核 |
| 关键字段缺失（金额/时间/账户） | 任一必填缺失 | 待核，计入影响金额清单 |
| 方向词不在该格式词表内 | 词表未收录 | 待核 |

**F 兜底语义**：F 同时是「未识别文件整体」与「行级异常」的处理出口——未识别文件整体进入待确认（不解析入库）；已识别文件中的行级异常按上表逐行进待核。两者都进待核清单，不得绕过。

### 4.2 转换顺序铁律

第一步判实际方向（依据格式规则 + 原金额符号 + 方向字段）→ 第二步金额按原始十进制字符串精确解析 → 第三步统一「收进为正、付出为负」。
**禁止**先取绝对值再套原始方向（会把冲回算反）。

### 4.3 单位换算与舍入（唯一规则）

**标准存储单位恒为「分」（整数最小货币单位，INTEGER）。** 入库倍率只有一种定义：

| 来源单位 | 存储单位 | 入库倍率 unit_scale |
|---|---:|---:|
| 元 | 分 | 100 |
| 分 | 分 | 1 |

- 微信类「分→元 除 100」只存在于显示层或外部中间格式，**绝不作为本软件入库倍率**；
- 金额解析：读**原始十进制字符串**（不经浮点），按 unit_scale 换算为分；
- 换算产生小数时**四舍五入到分**，±1 分差额在导入批次记录留痕，不静默丢弃；
- 来源单位记录在 format_rule.source_unit（如 '元'/'分'），fund_flow 行经 format_rule 关联可回溯，不靠倍率猜测；
- currency 默认 CNY，字段先建。

### 4.4 原值保存与规则版本化

- **双存**：原始值（raw_amount_text、raw_balance_text、raw_direction）与标准值（amount 带符号整数分、direction）并存；汇总只读标准值，复核走原始值。
- **规则版本化**：format_rule 含 rule_version、source_evidence（规则出处：模板文件/样本/人工确认）、verified 三态（0 未验证 / 1 已样本验证 / 2 已人工确认）、frozen 冻结标记；**「已验证必冻结」由表级 CHECK 强制**（verified=0 OR frozen=1）——验证动作必须在同一 UPDATE 中同时置 frozen=1，不能只靠调用者记得；冻结后不可原地改（触发器），变更必须新增 rule_version 行；fund_flow 行级记录 (format_rule_id, rule_version)——旧数据永远可找回当时的完整规则。
- **解析器版本**：import_batch 记录 parser_version，规则与解析器各自的版本都参与追溯。
- **frozen 写保护（数据库层）**：verified≥1 后 frozen=1；触发器拒绝任何原地 UPDATE、DELETE 或按主键/版本唯一键 REPLACE 覆盖冻结规则（RAISE ABORT），不能先解冻或删除再插入绕过；写入口同时校验 source_unit 与 unit_scale 配对（'元'↔100、'分'↔1），防「来源分、倍率100」式组合矛盾；变更一律新增 rule_version 行。

### 4.5 余额链校验（限域版）

**第一片只对「资产账面余额」执行校验公式，且仅当该格式规则已确认「amount 与余额增减同向」。**

- **校验式**（仅限上述口径）：上笔余额 + 本笔标准金额 = 本笔余额。
- **适用前提（全部满足才校验）**：同一账户、同一币种、balance_scope='asset_ledger'（资产账面余额）、流水段连续完整、同秒记录有稳定次序。
- **不适用场景**：欠款余额（信用卡欠款口径：消费支出使欠款**增加**，公式会算出相反差额）、可用余额与账面余额混用、退款/代扣等方向语义不同——一律标 balance_scope='debt'/'available'/'unknown'，**不套公式、标记「不适用/口径待核」**，仅展示。
- 标准资金流方向 ≠ 账面余额变化方向；余额校验只用于**发现异常**，绝不自动改向。
- 每个 balance_scope 的具体口径判定规则，由格式规则配置；格式未声明口径 → 'unknown'，不校验。

**当前结果与历史分层（2026-11-13，review-11 修订）**：每笔唯一的是 `balance_check` 当前结果指针；每次计算与人工接受追加到不可变 `balance_check_history`，不覆盖旧差额或依据。人工接受只能引用同笔、同输入版本的当前 fail；接受时原检查值保持不变，另存依据与时间。输入版本覆盖本笔、前项、规则/批次、余额口径和链段顺序/完整性；这些输入改变时，worker 须先使受影响旧结论失效，再重算，旧 manual 只留历史，不自动沿用。表结构与数据库/worker 的责任边界见 `03 §4.3`。

**金额状态与余额检查状态解耦（边界表）**：

| 情形 | 金额/方向状态 | 余额检查状态 |
|---|---|---|
| 金额方向可靠，但余额链不平 | 保持 confirmed | 异常（fail），不自动改金额 |
| 金额方向不确定 | pending | 不得用猜测金额判「通过」 |
| 人工接受余额异常 | 不随余额检查解除 | 仅该次检查标 manual |
| 无前项/顺序未定/口径未知/段落不完整 | 保留独立金额状态 | 不可比/未检查 + 原因 |

**待核行的呈现规则（并表、导出、汇总通用）**：

- 待核行在并表与导出中显式标注 pending，**不混入 confirmed 金额**；
- 汇总只计 confirmed 行；导出单独附「待核清单」（记录数、无法量化金额数、原因分布）；
- 影响金额无法量化时，**披露无法量化的记录数**，不得假装金额为 0。
- `fund_flow.status` 表示整条记录确认状态；金额、时间、账户等阻断原因分别保存在 `pending_reason`。worker 在同一事务内新增/解除逐项原因并核对聚合状态；仅确认金额、仍缺时间时继续 pending。余额 fail/manual 独立保存，不自动新增阻断原因或改变收支。

### 4.6 异常集中复核与待核清单

- 批量检查后集中展示：方向与金额矛盾、余额不平、换一种解释影响的笔数与金额；
- 审计人员确认规则后批量应用，少数例外单独处理；确认动作只作用于被确认项（如仅解除余额异常），不连带修改其他状态。
- 上述批量能力仍须经 `04 Q11` 确认范围；DeepSeek 赞同单笔优先的建议不等于用户已决定删减。当前先明确逐项依据与历史模型，是否开放时间/账户补录、撤销/重开仍见 `04 Q05`；本轮不增加这些操作。
