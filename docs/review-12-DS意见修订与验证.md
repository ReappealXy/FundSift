## 2. 数据设计具体变化

### 2.1 待核原因与记录状态

`pending_reason` 保存 `id / fund_flow_id / reason_code / detail / created_at / resolved_at / resolution_reason`。数据库约束保证来源记录存在、未解除的同码原因唯一、解除时间与非空依据成对；触发器拒绝删除、篡改创建事实或重开旧项。新发现的问题另建一项，不覆盖旧依据。

`fund_flow.status` 仍是记录确认状态。worker 必须同事务保存字段处理、逐项原因及聚合状态：解除金额原因后，若时间原因尚未解除，整行继续 pending；全部原因解除且关键字段满足规则才可 confirmed。**DDL 不自动执行这项聚合，当前探针只模拟协议 SQL，正式写入口尚未实现。**

余额差异和人工接受不自动生成记录阻断项，不改交易金额、方向或记录确认状态。

### 2.2 余额当前指针与历史

- `balance_check_history`：逐次追加检查或接受快照，包括 `input_version`、前项、预期/实际余额、差额、口径、原因及时间；manual 另有 `accepted_from_id / manual_reason / accepted_at`。
- `balance_check`：每笔至多一行当前指针，复合外键防止指向别笔历史。
- `balance_check_current`：页面查询完整当前检查的视图。

接受差异必须引用同笔、同输入版本的当前 fail，并原样保留原检查数值、原因和检查时间。接受时把差额改成零、空依据、错笔、错版本或引用过期检查，均由结构约束/触发器拒绝。

输入版本必须覆盖本笔、前项、规则/批次、账户/币种/口径及链段顺序与完整性。真实版本生成、受影响链段识别、失效与重算仍由 worker 实现。旧接受保留历史，新输入不能继承旧 manual；数据库不会自行检测所有业务输入变化。

### 2.3 探针发现并补上的绕过入口

实测发现 SQLite 的 `INSERT OR REPLACE` 可绕过普通 UPDATE/DELETE 保护。已增加插入前检查，禁止用 REPLACE 覆盖余额历史、待核项旧身份或尚未解除的同码项。

同一问题也影响冻结规则的不可变性，因此冻结规则同时拒绝 DELETE，以及按主键或规则版本唯一键 REPLACE；合法新版本仍可新增。AC-35 同步覆盖这些路径，错误单位倍率用未冻结规则作独立对照。
